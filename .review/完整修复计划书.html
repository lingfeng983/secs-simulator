0这份文档怎么来的

两份报告单独看都是对的，但直接拼在一起会得到一份自相矛盾的施工图：前端那份说"已全部修完、71 条 e2e 全绿"， 后端那份说"要删掉前端正在调用的 24 个端点"。如果照两份文档各自执行，第二阶段必然把第一阶段推翻。

所以整合的第一步不是合并章节，而是回答一个问题：这两份文档在哪些地方互相依赖？答案有三处：

接缝一 · 能力误判

前端有 3 处功能"做不了"，都归因为"后端能力限制"。核实后发现：其中 1 处后端其实早就实现了，是前端没接。

接缝二 · 测试基准

前端 71 条 e2e 跑在 v1 路径上，且刚全绿。后端删 v1 的那一刻，这 71 条会同时变红。

接缝三 · 术语分叉

前端已统一为"连接/已连接/未连接"，后端错误码仍是 bad-session-id。界面文案与后端 message 会对不上。

安全边界：从"恒为 ADMIN"到"必须出示凭证"

对应 P0-1　两个独立 PR，先安全后日志

AccessControl.java:51
HttpApiServer.java:withCors
RuntimeOptions（--bind）

现状AccessControl.authenticate() 无条件返回 LOCAL = new Principal("local", ApiRole.ADMIN)，角色检查形同虚设；withCors() 回 Access-Control-Allow-Origin: *；默认 --bind 0.0.0.0。

后果三者相乘：用户浏览器里任何一个网页，都能对这个后端发 POST /api/v1/shutdown、改设备配置、以主机身份发 SECS 报文。不需要知道 IP——浏览器会替攻击者找到本机。

判定不是"内网工具可以接受"的取舍。CORS 通配 + 零鉴权，攻击面是整个公网网页。

改法
  • 默认绑定改 127.0.0.1。对外提供必须显式 --bind 0.0.0.0，并在启动横幅用 WARN 打"正在监听所有网卡且未配置 token"。
  • 引入启动 token：未通过 --token 或 SECSSIM_TOKEN 指定时，生成随机 32 字节写入 <workDir>/token（0600）并打印路径。请求带 Authorization: Bearer <token>；SSE 沿用一次性票据，换票据时校验 token。
  • CORS 改白名单：只允许 http://127.0.0.1:*、http://localhost:* 与 --cors-origin 追加项。非白名单不回 CORS 头，并打一条 WARN。
  • 角色落到位：ApiRole 三级保留，requireRole() 不再恒通过；预留 --token role=viewer:xxx 解析入口。
  • 审计补齐：所有 POST/PUT/DELETE 已在 audit() 记录，补 principal 与来源 IP 两个字段——现在记了动作却没记是谁。
前端联动
  • api/base.ts 的 request() 统一注入 Authorization 头，token 从本地存储读。
  • 「连接设置」弹窗（修改地址）增加 token 输入框；后端返回 401 时弹出该弹窗并给出"在 <workDir>/token 查看"的提示。
  • SSE 换票据的请求也要带 token，否则 B0 合入后实时消息直接断。

8.1 schema 策略：版本不符就拒绝启动

现状 Schema.apply() 无条件把版本号 upsert 成当前值，写后不读：

// 现状：Schema.java:310-319
public static void apply(Connection connection, boolean configDatabase) throws SQLException {
    for (String ddl : (configDatabase ? CONFIG_DDL : RUNTIME_DDL)) {
        try (Statement st = connection.createStatement()) {
            st.executeUpdate(ddl);              // 全部 IF NOT EXISTS
        }
    }
    try (Statement st = connection.createStatement()) {
        st.executeUpdate("INSERT INTO meta(key, value) VALUES('schema_version', '"
                + VERSION + "') ON CONFLICT(key) DO UPDATE SET value=excluded.value");
    }                                        ← 旧库的版本号被直接覆盖成新版本
}

两个后果叠加：① IF NOT EXISTS 不会给已有表加列，改了 DDL 的库看起来"建表成功"但结构是旧的； ② 版本号被无条件改写，下一版程序再也无法判断这个库是新的还是旧的。 这正是 P0-3 的本质：不是"没有迁移脚本"，而是"连发现需要迁移的能力都没有"。

8.2 改法

// 目标：先读后判，不匹配就拒绝启动
public static void apply(Connection c, boolean configDatabase, Path dbPath,
                       boolean allowReset) throws SQLException {
    int found = readVersion(c);              // 无 meta 表 / 无该键 → 0
    if (found != 0 && found != VERSION) {
        if (!allowReset) {
            throw new IllegalStateException(
                "数据库版本不匹配：库为 v" + found + "，程序要求 v" + VERSION
                + "。本版本不提供迁移。请备份后删除 " + dbPath
                + " 再重启（运行态库可直接删；配置库删除后需重新导入设备配置）。"
                + " 确认要自动重建请加 --allow-schema-reset。");
        }
        recreate(c, dbPath);                  // 仅在显式开关下执行
    }
    createAll(c, configDatabase);
    writeVersion(c, VERSION);
}
情形行为理由
库不存在 / 空库建表并写版本首次启动
版本 == 当前正常启动唯一正常路径
版本 != 当前，无开关拒绝启动 + 明确报错不再静默跑错；错误信息直接给出下一步操作
版本 != 当前，带 --allow-schema-reset删库重建把"破坏性"变成一次显式确认，而不是隐式发生

刻意不做"自动 ALTER"和"逐版本迁移链"。理由不是偷懒：一个没有迁移机制的版本，比一个半吊子迁移机制更安全—— 后者会在某次漏写 ALTER 时把库改成"一半新一半旧"，这种现场极难复现。拒绝启动至少是确定的、可恢复的。

④ 堆栈输出

private static void appendCause(StringBuilder sb, Throwable cause) {
    StringWriter sw = new StringWriter(512);
    cause.printStackTrace(new PrintWriter(sw));
    for (String line : sw.toString().split("\n")) {
        sb.append("\n        ").append(line);      // 缩进对齐，便于 grep "at com.shimizukenta"
    }
}

默认策略：ERROR 打完整堆栈；WARN 只打异常类型 + 首帧；INFO/DEBUG 不打。这比"全部打"或"全都不打"都实用——日志文件不会因降级事件膨胀，也不会在关键错误上缺信息。

⑤ 访问日志

// HttpApiServer：出口统一打一行，覆盖所有 handler，不需要每个 handler 自己记
long t0 = System.nanoTime();
try {
    handler.handle(ex);
} finally {
    long ms = (System.nanoTime() - t0) / 1_000_000L;
    if (ms >= SLOW_MS) {
        ACCESS.warn("{} {} {} {}ms", method, path, status, ms);
    } else {
        ACCESS.info("{} {} {} {}ms", method, path, status, ms);
    }
}

慢请求（≥1000ms）升 WARN，与现有"慢请求专用池"的判定口径统一。这一条同时解决"没有访问日志"和"慢请求不可见"两个问题，也让 P0-1 的安全事件第一次有取证依据。

⑥ 级别判定规则

级别判定示例
ERROR用户请求失败，或数据可能不一致且无法自愈，需要人介入配置保存失败、会话启动失败（端口占用）、schema 版本不匹配
WARN已降级但业务继续，或需要后续处理，不阻断当前操作审计日志写失败（继续运行）、SSE 连接达上限、慢请求、落库失败但业务已生效
INFO状态变迁，一条事件一行，生产默认开启会话启动/关闭、配置保存成功、级别切换、访问日志、启动横幅
DEBUG排障时才需要，生产关闭报文收发摘要（流号 + 长度，不含正文）、SQL 耗时
TRACE逐帧/逐行，默认永不开启SML 全文、HSMS 帧十六进制

判定口诀：这次操作成功了没有？ 没成功 → ERROR；成功了但有东西没落地 → WARN；成功了且一切正常 → INFO。

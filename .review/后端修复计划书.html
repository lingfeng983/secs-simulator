0计划边界

一句话概括本计划：把三套并存的语义收成一套，把为"未来"预付的成本全部退掉，把看不见的运行状态变成能看见的日志。 除此之外不加任何新功能。

本计划做什么

  • 补齐安全边界（鉴权 / CORS / 绑定地址）
  • 身份统一：会话 id = 设备 ULID，删除 legacy 别名
  • 删除全部 v1 设备域端点与兼容写法
  • 删除 11 张投影表与整个投影写入链
  • schema 版本不符即拒绝启动
  • 重写日志层：堆栈 / 来源 / 参数化 / 五档 / 访问日志

本计划明确不做

  • 不做 v1→v2 数据迁移脚本
  • 不做 旧 config.db 的 ALTER / 兼容读
  • 不做 v1 端点"降级为只读别名"的过渡期
  • 不保留 Deprecation / Sunset 头
  • 不加 多用户、多租户、RBAC 细化
  • 不改 SECS 协议栈行为与报文语义

完成判据（Definition of Done）

  • 代码库中搜不到 /api/v1/sessions、/host-sims、legacy_id
  • 代码库中搜不到 PROJECTION_TABLES、ConfigProjector
  • 全部日志调用点无字符串拼接、无 null 传参
  • 旧库启动时给出明确报错而非静默跑错
  • 前端所有请求命中新路径，无 404/400
  • e2e 脚本全绿

为什么可以"不考虑迁移"

这个取舍成立，依赖三条前提，三条都必须为真，否则 B3 要降级为一次性离线迁移脚本：

#前提核验方式当前判定
1 数据可再生 runtime.db 全部是运行态（链路相位、台账、钉值），删了重启就重建；config.db 里的设备配置、主机模板、计划可从 UI 重新导入或重新配置。 成立
2 无外部依赖方 除自带前端 secs-simulator-ui 与 scripts/tools/host-e2e 外，无第三方系统调用本 API。前端与 e2e 都在本仓库内，可同批改。 成立
3 部署形态是单机内网工具 无 SaaS 多实例、无灰度发布需求，允许"停机 → 删库 → 重启"的升级方式。 需产品确认

第 3 条是唯一需要产品负责人签字的地方。如果将来出现"客户现场不能删库"的场景，本计划第 7 章的 schema 策略必须改为"版本不符 → 提示用户导出配置 → 自动重建 → 导入"， 也就是把"迁移"换成"导出/导入"，仍然不需要写 ALTER 脚本。这一点在 B3 的设计里已经预留了开关（见 7.3）。

安全边界：从"恒为 ADMIN"到"必须出示凭证"

对应 P0-1　两个独立 PR，先安全后日志

AccessControl.java:51
HttpApiServer.java:withCors
RuntimeOptions（--bind）

现状AccessControl.authenticate() 无条件返回 LOCAL = new Principal("local", ApiRole.ADMIN)，角色检查形同虚设；同时 withCors() 回 Access-Control-Allow-Origin: *，且默认 --bind 0.0.0.0。

后果三者相乘等于：用户浏览器里任何一个网页，都能对这个后端发 POST /api/v1/shutdown、改设备配置、以主机身份发 SECS 报文。不需要知道 IP——浏览器会替攻击者找到本机。

判定这不是"内网工具可以接受"的取舍。CORS 通配 + 零鉴权，攻击面是整个公网网页，而不是内网。

改法
  • 默认绑定改为 127.0.0.1。要对外提供时必须显式 --bind 0.0.0.0，并在启动横幅里用 WARN 打一行"正在监听所有网卡，且未配置 token，任何本机浏览器页面均可操作本服务"。
  • 引入启动 token：进程启动时若未通过 --token 或环境变量 SECSSIM_TOKEN 指定，则生成随机 32 字节、写入 <workDir>/token（权限 0600）并在启动横幅打印路径。请求需带 Authorization: Bearer <token>；SSE 沿用现有一次性票据机制，票据换取时校验 token。
  • CORS 改为白名单：只允许 http://127.0.0.1:* 与 http://localhost:*，以及 --cors-origin 显式追加的来源。非白名单来源不回 CORS 头（浏览器自然拒绝），并在访问日志打一条 WARN。
  • 角色落到位：ApiRole 的 VIEWER/OPERATOR/ADMIN 三级保留，requireRole() 不再恒通过。token 单角色时按 ADMIN 处理，但预留 --token role=viewer:xxx 的解析入口，避免将来又要改一遍中间件。
  • 审计补齐：所有 POST/PUT/DELETE 已在 audit() 里记录，需补上 principal 与来源 IP 两个字段——现在记了动作却没记是谁。

5.2 关键代码：P0-2 是怎么被彻底消除的

现状——RuntimePersister.key() 在查库失败时返回原键，于是同一个设备可能以两种键写进 runtime.db：

// 现状：RuntimePersister.java:164-172
private String key(String id) {
    try {
        String canonical = this.deviceKey.apply(id);
        return canonical == null || canonical.isBlank() ? id : canonical;
    } catch (RuntimeException e) {
        // 配置库临时读不了：退回原键，宁可让运行态暂时归错也不能把请求带崩
        return id;              ← P0-2：ULID 解析失败即写出读不到的孤儿行
    }
}

改后——没有"另一个键"可退回，也就不存在归错的可能：

// 目标：没有 key()，id 就是键
void savePin(String deviceId, long svid, double value) {
    this.state.pinSvid(deviceId, svid, value);   // deviceId 恒为 ULID
}

这是本计划最核心的一处判断：P0-2 不能靠"把兜底写得更谨慎"修好。只要双键存在，就一定有某条路径在某次异常时写错键； 只有消灭双键，缺陷才是"不可能发生"而不是"这次没发生"。

5.3 补回会话销毁（P0-4）

现状DELETE /api/v1/sessions/{id} 曾被改为"断链"语义后移除，但 ApiContextSessionOps.closeSession() 仍在，且没有任何 HTTP 调用方。结果是：通过 API 起来的会话，没有任何办法通过 API 停掉——只能重启进程。

改法新增 DELETE /api/v2/devices/{id}/session，语义明确为"停止该设备的运行会话，保留配置与运行态编辑"，返回 204；设备无会话时返回 404（而不是静默 200，避免前端以为关成功了）。同时 closeSession() 补上调用方，从死代码复活。

7.1 schema 策略：版本不符就拒绝启动

现状 Schema.apply() 无条件把版本号 upsert 成当前值，写后不读：

// 现状：Schema.java:310-319
public static void apply(Connection connection, boolean configDatabase) throws SQLException {
    for (String ddl : (configDatabase ? CONFIG_DDL : RUNTIME_DDL)) {
        try (Statement st = connection.createStatement()) {
            st.executeUpdate(ddl);              // 全部 IF NOT EXISTS
        }
    }
    try (Statement st = connection.createStatement()) {
        st.executeUpdate("INSERT INTO meta(key, value) VALUES('schema_version', '"
                + VERSION + "') ON CONFLICT(key) DO UPDATE SET value=excluded.value");
    }                                        ← 旧库的版本号被直接覆盖成新版本
}

两个后果叠加：① IF NOT EXISTS 不会给已有表加列，改了 DDL 的库看起来"建表成功"但结构是旧的； ② 版本号被无条件改写，下一版程序再也无法判断这个库是新的还是旧的。 这正是 P0-3 的本质：不是"没有迁移脚本"，而是"连发现需要迁移的能力都没有"。

7.2 改法

// 目标：先读后判，不匹配就拒绝启动
public static void apply(Connection c, boolean configDatabase, Path dbPath,
                       boolean allowReset) throws SQLException {
    int found = readVersion(c);              // 无 meta 表 / 无该键 → 0
    if (found != 0 && found != VERSION) {
        if (!allowReset) {
            throw new IllegalStateException(
                "数据库版本不匹配：库为 v" + found + "，程序要求 v" + VERSION
                + "。本版本不提供迁移。请备份后删除 " + dbPath
                + " 再重启（运行态库可直接删；配置库删除后需重新导入设备配置）。"
                + " 确认要自动重建请加 --allow-schema-reset。");
        }
        recreate(c, dbPath);                  // 仅在显式开关下执行
    }
    createAll(c, configDatabase);             // 仍用 IF NOT EXISTS，但只在版本匹配时走到
    writeVersion(c, VERSION);
}
情形行为理由
库不存在 / 空库建表并写版本首次启动
版本 == 当前正常启动唯一正常路径
版本 != 当前，无开关拒绝启动 + 明确报错不再静默跑错；错误信息直接给出下一步操作
版本 != 当前，带 --allow-schema-reset删库重建把"破坏性"变成一次显式确认，而不是隐式发生

这里刻意不做"自动 ALTER"和"逐版本迁移链"。理由不是偷懒，而是：一个没有迁移机制的版本，比一个半吊子迁移机制更安全—— 后者会在某次漏写 ALTER 时把库改成"一半新一半旧"，而这种库的故障现场极难复现。 拒绝启动至少是确定的、可恢复的。

④ 堆栈输出

private static void appendCause(StringBuilder sb, Throwable cause) {
    StringWriter sw = new StringWriter(512);
    cause.printStackTrace(new PrintWriter(sw));
    for (String line : sw.toString().split("\n")) {
        sb.append("\n        ").append(line);      // 缩进对齐，便于 grep "at com.shimizukenta"
    }
}

默认策略：ERROR 打完整堆栈；WARN 只打异常类型 + 首帧（降级事件通常不需要完整调用链，但需要知道来源）； INFO/DEBUG 不打。这比"全部打"或"全都不打"都更实用——日志文件不会因为降级事件膨胀，也不会在关键错误上缺信息。

⑤ 访问日志

// HttpApiServer：出口统一打一行，覆盖所有 handler，不需要每个 handler 自己记
long t0 = System.nanoTime();
try {
    handler.handle(ex);
} finally {
    long ms = (System.nanoTime() - t0) / 1_000_000L;
    if (ms >= SLOW_MS) {
        ACCESS.warn("{} {} {} {}ms", method, path, status, ms);
    } else {
        ACCESS.info("{} {} {} {}ms", method, path, status, ms);
    }
}

慢请求（≥1000ms）升 WARN，与现有"慢请求专用池"的判定口径统一。这一条同时解决了"没有访问日志"和"慢请求不可见"两个问题， 也让 P0-1 的安全事件第一次有了取证依据（谁在什么时候调了 shutdown）。

⑥ 级别判定规则（写进代码注释，作为 review 依据）

级别判定示例
ERROR用户请求失败，或数据可能不一致且无法自愈，需要人介入配置保存失败、会话启动失败（端口占用）、schema 版本不匹配
WARN已降级但业务继续，或需要后续处理，不阻断当前操作审计日志写失败（继续运行）、SSE 连接达上限、慢请求、落库失败但业务已生效

DEBUG排障时才需要，生产关闭报文收发摘要（流号 + 长度，不含正文）、SQL 耗时、投影重算
TRACE逐帧/逐行，默认永不开启，需显式 PUT /log-level traceSML 全文、HSMS 帧十六进制

9.6 关于"要不要换成 logback / slf4j"

不建议换。现有 Log 的注释写明是为原生镜像体积而自研，这个约束是真实的。 本章的改动全部在原类内完成，约 420 行，不引入任何依赖，也不改变原生镜像的构建方式。 真正的问题从来不是"没用框架"，而是"用了自研却没把它当基础设施做"——三档级别、不打堆栈、没有来源，这些与是否用框架无关。

10不写迁移的代价与红线

#代价具体表现缓解
1升级必须删库 旧 config.db 无法启动（B3 后主动报错）。用户手工配的设备、主机模板、计划会丢失。 B3 的报错信息里直接给出路径与操作步骤；发布说明里写清"升级前请用 UI 导出设备配置"
2无法回滚到旧版本 新库结构与旧版本不兼容，回退程序同样启动失败。 回滚方案 = "回退程序 + 恢复备份的旧库"。要求 --allow-schema-reset 执行前先自动备份到 config.db.bak.<时间戳>
3现场升级需要人工在场 不能静默自动升级。 这是特性而非缺陷：静默删用户数据的自动升级比停机人工升级危险得多
4e2e 与测试数据需重建 scripts/tools/host-e2e 依赖的初始配置、单测里的 fixture 都要改。 B2/B3 合并前先跑一遍 e2e，把 fixture 一起改；SimHost.java 里硬编码的 v1 路径必须同批改

三条红线（任何一条不成立，本计划需重新评估）

  • 红线 1：config.db 中的内容必须能从 UI 重新录入或在 30 分钟内重建。若存在"客户现场只此一份、无人知道怎么配"的实例，禁止合入 B3。
  • 红线 2：发布方式必须是"停机升级"，不能是"滚动升级 / 灰度"。多实例并存期间两版 schema 会互相破坏。
  • 红线 3：--allow-schema-reset 必须在备份成功后才会真正删库，且备份路径要打进日志。不允许"删了才发现没备份"。

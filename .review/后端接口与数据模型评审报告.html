后端接口与数据模型评审报告

以负责人 / 架构师 / 产品经理三重身份，对 secs-simulator-service 的 全部 HTTP 端点与全部数据库表做一次存在性与合理性评审。结论不是"能不能跑"， 而是"这一层该不该长成现在这样"。

评审对象 8 个模块 / 481 个源文件 / 66.7k 行 接口 约 50 个路由组、110 个方法+路径 数据表 30 张（config.db 20 / runtime.db 10） 日期 2026-11-18

0摘要与判定

这套后端的单点工程质量很高——错误码分得很细、并发与慢请求有隔离、超时与停滞检测、 幂等键、乐观锁、软删、台账异步批写，这些都不是随手写出来的。问题不在"某一处写错了"， 而在三次架构演进没有收敛：v1 会话模型、v1 主机实例模型、v2 实体模型三套语义同时在线， 数据层则为一次尚未发生的"结构化查询"预建了 11 张零读者的投影表。 接口层需要做的是减法与收口，不是继续加端点。

1五条核心结论

#结论依据影响
1 实体模型有三套名字 同一个东西在不同层叫 config（v1 配置）、session（v1 运行实例）、device（v2 实体）。 v1 用 /api/v1/configs 建设备、/api/v1/sessions 起实例； v2 用 /api/v2/devices/{id} 操作同一批对象，且 v2 没有集合端点， 客户端仍要回头读 /api/v1/configs 才能列出设备。 认知成本 / 客户端复杂度
2 同一能力有三代实现 主机模拟：/sessions/{id}/host-sim → /host-sims/{id} → /api/v2/hosts/{id}。 运行时编辑：/sessions/{id}/{events,reports,ceids,svids} → /api/v2/devices/{id}/runtime/catalog。 预览：/preview / /preview.bin / /config-preview。 三套都活着、都在被调用、错误码各不相同。 维护成本 / 缺陷面
3 数据层为"未来"付了现价 config.db 20 张表里有 11 张是投影表，全代码库零处 SELECT； 每次保存配置都要在全局写锁内对 11 张表做 DELETE + 逐行 INSERT。 device_link 另有 3 个从未写入的列。 写延迟 / 磁盘 / schema 负担
4 身份靠"查表推导"而非约束 runtime.db 的所有行都用 config.db 的 ULID 做键，但这个 ULID 不是存下来的， 而是每次写入前 findDevice() 查出来的；查不到就静默退回 legacy stem。 同一台设备可能同时存在两套键的行，读的时候只认其中一套。 数据静默丢失
5 安全边界是"声明式"的 requireRole 遍布全部端点，但 AccessControl.authenticate() 恒返回 local/ADMIN；同时响应头 Access-Control-Allow-Origin: *， 默认监听 0.0.0.0。角色分层在运行时不产生任何效果。 任意网页可控制设备

2架构师视角

2.1 模块边界与依赖方向 —— 这一层做对了

secs-store / secs-app / secs-runtime / secs-api-http

现状 secs-store 不认识业务类型，投影通过 DocumentProjector 回调注入； secs-api-http 只认 ApiContext 接口，不认运行时实现。依赖方向单向、可测， 这是全项目最值得保留的架构决定。

问题 但 ApiContext 本身就是新的耦合点：4 个父接口 + 本体共 132 个方法 （128 个 default + 4 个抽象），每个 handler 都拿到全集。任何一处新增能力都要动这个接口， 而绝大多数调用方只用其中 2–3 个方法。

建议
  • 按 handler 收窄注入：SessionHandler 只依赖 SessionOps， PlanExecutionsHandler 只依赖 PlanOps，不要再传 ApiContext 全集。
  • 删掉无调用方的接口方法（见 §7 P2-3），它们是接口膨胀的主要来源。

2.2 三代 API 并存：需要一次明确的收敛

ApiPaths.java · HostSimHandler · SessionHostSimRoutes · DeviceRuntimeHandler

现状 主机模拟这一个能力，现在有三套完全独立的实现路径：

代入口定位键仍在使用
1/api/v1/sessions/{id}/host-sim[/send|/collector]会话 id是（前端仍在调）
2/api/v1/host-sims[/{id}][/send|/collector|/burst]实例 id是（collector 走这条）
3/api/v2/hosts[/{id}][/connect|/send|/plans|/messages]持久主机 id是（主机页走这条）

问题 三套的 SML 大小上限、错误码、鉴权位置都各自演化过（代码注释里记录了至少三次 "两条路径同义却给不同上限"的修复）。这不是重复代码问题，是同一份契约有三个真值来源—— 任何一次行为调整都必须同时改三处，否则界面会按入口不同表现不同。

建议
  • 定一条硬规则：v2 是唯一写入面。v1 的两套主机端点降级为"只读别名 + Deprecation/Sunset 头"， 不再接受新的行为改动。
  • 前端在 3.x 内迁完 /api/v1/host-sims/*/collector 与 /api/v1/sessions/*/host-sim， 4.0 删除。
  • 把 statusOf(SessionOutcome) 这类映射收成一份公共实现——目前 HostSimHandler 里有私有副本，DeviceLinkHandler / DeviceRuntimeHandler 各写了一遍 switch。

2.3 设备身份双键：最需要立刻处理的数据问题

DeviceIdResolver.java:31 · RuntimePersister.java:164 · ConfigRepository.java:449

现状 device.id 是 ULID（dev_01J…），device.legacy_id 是 v1 的配置文件名（line1）。runtime.db 所有表都用 ULID 做 device_id， 但这个 ULID 不随请求传递——每次写入前由 RuntimePersister.key() 调 ConfigRepository.findDevice() 现场查出来。

问题 关键在 RuntimePersister.java:168：查库抛异常时 回退到原始 key（即 legacy stem）继续写。于是一次瞬时读失败就会在同一台设备下 写出两套键的行；之后所有读取都按 ULID 查，那批 stem 键的行就变成永远读不到的孤儿—— 用户看到的现象是"钉值/计划启用态/目录编辑丢了"，日志里只有一条 warn。

同样的问题在 DeviceIdResolver.sessionFor()：它对每个会话调一次 canonical()（一次连库 + 两条 SELECT），O(n) 次跨库查询/请求。 20 台设备时，一次 GET /runtime/executions 就是 20 次建连 + 80 条 PRAGMA + 40 条 SELECT。

建议
  • 写入必须确定：key() 解析失败时拒绝写入并返回错误，绝不回退。 宁可这次钉值不生效，也不能写进一个读不到的键。
  • 在 device 表上给 legacy_id 建索引（已有 idx_device_legacy）， 并在进程内加一层 sessionId → ULID 的缓存，注册/注销时失效，去掉热路径上的跨库查询。
  • 更彻底的做法：让会话 id 直接等于 ULID，legacy stem 只做只读别名映射。 这是 4.0 应该做的事，越早越好。

2.4 存储层：双库设计成立，但实现有三处不该有的代价

Db.java:200-217 · ConfigRepository.java:534 · Schema.java

现状 config.db（权威、有版本、软删）+ runtime.db（可丢弃重建）物理隔离，这个切分是对的： 备份只需备份前者，后者损坏可以直接删。写路径单写者 + BEGIN IMMEDIATE 也符合 SQLite 的最佳实践。

问题一：一把锁锁两个库。 writeConfig 与 writeRuntime 同步在同一个 writerLock 上。两个库各有独立连接、彼此没有事务关系，共用一把锁的唯一效果是： plan_execution 每 50ms 一次的批写会挡住配置保存，反之亦然。

问题二：读连接不复用且每次都跑 4 条 PRAGMA。 Db.readConfig() 每次新建连接后执行 journal_mode / foreign_keys / busy_timeout / synchronous。WAL 是库级持久属性， 对每条读连接重复设置纯属浪费；配合 §2.3 的 N+1，这部分开销被放大了 n 倍。

问题三：投影表全量重建。 reproject() 对 11 张表先 DELETE 再逐行 INSERT， 全部发生在持有写锁的事务里。而没有任何代码读这些表（见 §6）。

建议
  • 拆成两把锁（configLock / runtimeLock），两库互不阻塞。
  • 读路径改成小型连接池（8–16 条即可），PRAGMA 只在建连时跑一次。
  • 投影表：要么删掉，要么改成 VIEW（SQLite 支持 json_extract 直接查正文）， 永远不要"物化一份没人看的数据"。

2.5 安全边界：声明了角色，但没有身份

AccessControl.java:29 · HttpApiServer.java:604 · RuntimeOptions.java:131

现状 ADR 0018 明确"内网工具不做鉴权"，AccessControl.open() 恒返回 local/ADMIN。所有 requireRole(ex, VIEWER/OPERATOR/ADMIN) 都是装饰。

问题 真正的风险不是"内网信任同事"，而是浏览器： withCors 对所有响应加 Access-Control-Allow-Origin: *， 并放行 Content-Type 与 If-Match 的预检。这意味着 用户在这台机器上打开的任何网页都可以：POST /api/v1/shutdown 关掉服务、 PUT /api/v1/configs/{name} 改写设备配置、POST .../runtime/message 向产线主机发报文。 默认 --bind 0.0.0.0 再把这个面扩到整个局域网。

建议（按成本从低到高，前两条建议立即做）
  • 默认 --bind 127.0.0.1；需要局域网访问时显式 --bind 0.0.0.0 --allow-lan。
  • CORS 不要 *：无 Origin 的请求（curl/桌面端）照常放行； 带 Origin 的浏览器请求只在同源或白名单时回 Allow-Origin，否则不回该头。
  • 启动时生成一次性 token 写入 work-dir/.token，前端从本地文件/启动参数拿到； AccessControl 改成一个真正校验 token 的实现，requireRole 的代码一行都不用动 （这正是当初预留 Principal 的目的）。
  • /shutdown、/audit、DELETE /runtime/executions 这类端点， 在 token 模式下落成真正的 ADMIN。

2.6 并发与长连接：设计到位，两个细节要补

HttpApiServer.java:604-682 · StreamHandler.java:153-175

现状 虚拟线程 + 慢请求专用池 + 请求截止时间 + SSE 写停滞看门狗 + 每订阅者 256 帧有界队列， 这套组合处理了 JDK HttpServer 最常见的几个坑（keep-alive 占线程、慢正文、客户端不读），做得比多数项目扎实。

问题一：票据在容量拒绝时被烧掉。 handleEvents 先 consumeTicket() 再 sseExecutor.execute()；池满抛 RejectedExecutionException 时票据已经消费，客户端拿到 503 后 用同一个 URL 重试只会得到 401。

问题二：慢请求判定靠路径字符串。 isSlowRequest 用 path.contains("/host-sim") 这类后缀匹配，设备名里恰好带 host-sim 就会被误分类；新增端点也容易漏。

建议
  • 票据改成"先占坑再消费"：容量检查通过后再 remove(ticket)，失败时把票据放回。
  • 慢路由改为路由表上的显式标记（注册时传一个 Route(slow=true)），不要靠路径猜。

3产品经理视角

3.1 功能闭环：三个"用户一定会撞上"的断点

SessionHandler.java:330 · ConfigRepository.java:371 · ApiPaths.java:84

断点一：设备关不掉。 3.0 把 DELETE /api/v1/sessions/{id} 的语义改成了 "只断链、不删实体"，方向是对的（符合"关闭 = 断链不删实体"的需求），但没有提供新的销毁端点。 后果：断链后会话仍在注册表里，再 POST /api/v1/sessions 建同名会话直接 409。 用户唯一的出路是删配置（DELETE /configs/{name}），而那会连带清空钉值、 计划启用态、目录编辑——比"关掉一台设备"重得多。

断点二：版本历史只能看列表，看不到内容、回滚不了。 ConfigRepository.readRevision() 已经写好（"回滚用"），但没有任何端点调用它； GET /api/v2/devices/{id}/config/revisions 只返回 revision/sha/时间/人。 用户在界面上看到"v7 是张三昨天改的"，点不进去，也退不回去。

断点三：v2 没有设备集合。 /api/v2/devices/ 只挂了 {id}/…， GET /api/v2/devices 会落到静态兜底返回 404。所以"列出设备"永远只能走 GET /api/v1/configs，返回的字段里没有 id——v2 的实体标识对客户端不可见， 只能拿文件名去调 v2 端点。

建议
  • 新增 DELETE /api/v2/devices/{id}（销毁会话 + 释放 id，保留配置行）， v1 的 DELETE 保持"断链"并加 Deprecation。
  • 新增 GET /api/v2/devices/{id}/config/revisions/{rev}（取某版正文）与 POST …/config/rollback（以某版正文走一次正常保存，产生新版本而不是覆盖历史）。
  • 新增 GET /api/v2/devices，返回 id / name / revision / autoStart / linkPhase； GET /api/v1/configs 至少在响应里补上 id。

3.2 契约信息丢失：后端算了，但没告诉客户端

SessionHandler.java:102 · ConfigHandler.java:404 · RuntimeApi.java:1131

现状与问题 三处典型：

  • POST /api/v1/sessions 成功只回 {"ok":true}，不回 sessionId。 客户端只能再拉一次列表猜哪个是刚建的。对比 v2 的 POST /api/v2/hosts 已经会回 hostId——同一个项目两种做法。
  • PUT /api/v1/configs/{name} 成功只回 {"ok":true}。 编辑器必须再 GET 一次拿 modifiedMs 才能让下一次保存的 If-Match 对得上 （前端 ConfigPanel.tsx:207 正是这么补的）。这次 GET 失败，下一次保存就必然 409。
  • warnStaleSessions() 已经算出"哪些会话还在用旧配置"，结果只写进日志， 响应体里一个字都不带。前端只好自己编了一句"相关会话已按新配置重启"的提示——而实际上 并没有重启（只有分段保存才有守卫与应用逻辑）。这是一条会误导用户的假提示。
建议
  • 写操作一律回"变更后的状态"：{"ok":true,"id":…,"revision":…,"modifiedMs":…,"staleSessions":[…]}。
  • 把 staleSessions 提到响应体，前端据此显示"3 台设备仍在用旧配置，点此重载"。

3.3 语义命名：configs 其实是 devices

ApiPaths.java:45 · README.md:169

问题 /api/v1/configs 的 GET 返回设备清单、POST 建设备、DELETE 删设备， 但名字叫"配置"。真正的"配置正文"是它的子资源。这导致三处解释成本： 新人要花时间搞清 config / session / device 的关系；README 的表格里 "新建配置"其实是"新建一台设备"；错误码 config-exists 其实是"设备名已存在"。

建议
  • v2 已经把名字摆正（devices），v1 保持不动但文档必须写清 "v1 的 configs ≡ v2 的 devices"。
  • 新错误码不要再用 config-* 前缀；v1 存量错误码在 4.0 随端点一起下线。

4负责人视角：该不该做、先做什么

值得肯定的三个决定

  • 配置正文存原文（不是反序列化模型）。编辑器能看到用户写的每一个键， 这是配置类工具最容易被做错的地方，这里做对了。
  • 软删 + 版本快照。设备删掉之后"它上周为什么报警"仍查得到，符合排障场景。
  • 分段保存 + 三道守卫。结构变更要求下线、周期引用的 SVID 禁改、常量覆盖二次确认—— 这是真正从产线事故里长出来的设计。

应该立刻停止的三件事

  • 停止新增 v1 端点。 每加一个 v1 端点，未来就多一处要迁。
  • 停止为"未来查询"预建表。 11 张零读者投影表就是前车之鉴。
  • 停止"注释里写清楚"代替"接口上表达"。 health 的 extraHealthJson 靠"必须以逗号开头"的字符串约定， burst 的 GET 靠哨兵 body {"status":true}， 这类约定只有读源码的人知道。

/ 静态资源GET无合理 SPA 回落只对无扩展名路径生效、/api/* 不回落、路径穿越有校验——细节都对。 不足：Files.readAllBytes 全量入内存、无 gzip、无 Range，前端 bundle 每次冷启动都整份传输。 建议至少对 .js/.css 加 gzip（或让反向代理处理）。

6.1 config.db（20 张）

表读用途判定问题与建议
device是设备实体核心 设计正确（ULID 主键 + legacy_id 别名 + 软删 + 部分唯一索引）。缺陷：deleteDevice 把 legacy_id 置 NULL 以便名字复用，但 name 的唯一索引只约束未删行， 两者行为不一致；auto_start 列无任何写入口（创建时恒 1，之后不可改）。

config_revision是版本快照需改 每版存全文，保留 200 版。一份 80KB 的多腔体配置 → 单设备 16MB。且最新版与 config_document.body 完全重复。建议：按 content_sha256 去重存正文 （正文表 + 引用表），或保留 N 版 + 按需归档。
connection_spec0投影：连接参数零读者 11 张投影表全部零读者。

它们在每次保存时被 reproject() 整体 DELETE + 逐行 INSERT （ConfigRepository.java:534-547），全部发生在持有全局写锁的事务里； 而代码库中不存在任何 FROM <这些表> 的查询。 唯一的写入方 ConfigProjector 有 422 行。

这意味着：每一次配置保存都要多写几百到几千行没人读的数据， 并且这些表的结构会永久占用 schema 演进的维护成本。

建议（三选一，按成本排序）：
  1. 直接删除 11 张表与 ConfigProjector（最省事，风险最低——没有读者就没有回归面）。
  2. 改成 VIEW，用 SQLite 的 json_extract(body,'$.…') 按需展开。
  3. 如果确实规划了"结构化查询"，把它做成独立的只读索引库，异步重建， 不进入写事务、不占写锁。
equipment_spec0投影：设备规格零读者
unit_def0投影：单元零读者
svid_def0投影：状态变量零读者
equipment_constant0投影：常量零读者
report_def0投影：报告零读者
report_svid0投影：报告成员零读者
ceid_def0投影：采集事件零读者
ceid_report0投影：事件-报告零读者
event_plan0投影：编排计划零读者
plan_action0投影：计划动作零读者
device_template是设备模板需改 内置 + 自定义统一入库、readonly 控制可写性，模型合理。 问题：主键是客户端提供的 id（bare/smt），无长度/字符约束， 与 param_template 用 pt_ ULID 的策略不一致。
param_template是参数模板可合并 与 device_template 结构几乎完全相同，只差列名（name vs label） 与 id 策略。建议合并成 template(kind, id, name, description, body, source, readonly)。
host_template是主机模板合理 字段与 host 高度重复（collector_json 两份），但"模板 ≠ 实例"的语义成立。 缺：name 无唯一约束（同名模板可以建无数个）。
host是主机实体需改 与设备无任何引用（设计 P6，正确）。缺：name 无唯一约束（对比 device 有）， 重名主机在界面上无法区分；setting_revision 与 runtime 的 host_link.applied_revision 构成"待生效"判断，逻辑正确但跨库无约束。
host_plan是主机方案库需改 主键 (host_id, kind, plan_id)，upsert 正确。问题：主机软删后方案行残留 （cleanupOrphans 只清 runtime.db），成为永久孤儿；body 是前端结构原样 JSON， 服务端不做任何校验，方案格式漂移时无法在写入期发现。
meta是键值元数据未兑现 schema_version 只写不读：Schema.apply() 每次启动无条件覆盖成 VERSION，没有任何"读到旧版本 → 执行迁移"的分支。而建表全部是 CREATE TABLE IF NOT EXISTS——它不会给已存在的表加列。 结论：下一次 schema 变更（加一列）在已有工作目录上会静默失败（新列不存在 → 运行期 SQL 报错）， 或者要求用户删库重建。这是当前最危险的一处技术债（见 §7 P0-3）。

6.2 runtime.db（10 张）

表读用途判定问题与建议
device_link是设备链路相位需改 三个死列：counters_json / overrides_json / last_good_json 全代码库从未写入（只有 LinkRow 读取后丢弃）。后两者与专门的 runtime_plan_override / runtime_catalog_edit 表职责重叠，属于早期设计的残留。 建议删除三列。另：phase 是自由字符串，无 CHECK 约束，拼错不会被发现。
host_link是主机链路相位合理 含 retry_count / next_retry_at，支撑自动重连退避，设计到位。 与 device_link 字段不对称（缺 control_state）——这是合理的，主机没有 GEM 控制态。
runtime_plan_state是计划运行统计需改 双源问题：enabled 与 config 的 event_plan.enabled_default 都表达"默认启用"， 以谁为准没有单一规则。PlanExecutionRepository.upsertFires 在行不存在时 硬编码插入 enabled=1（:225），而不是取配置默认值—— 如果某计划的 enabled_default=0 且从未启停过，第一次触发就会把它写成"已启用"。
plan_execution是执行台账设计好 幂等键 UNIQUE + 异步批写 + 保留策略 + 按设备裁剪，是全项目数据层最成熟的一张表。 小问题：缺 (device_id, status) 索引（查询支持 status 过滤）；message_json/effect_json 存 JSON 文本，无法按字段过滤；trim() 每小时跑一次全表窗口函数，设备多时会短暂占写锁。
runtime_svid_pin是钉值合理 主键 (device_id, svid)，upsert 正确。值是 REAL——SECS 的 SVID 可能是 A/U1/U2/U4/F4/F8， 用 REAL 存会丢失整数精度与字符串型值。若当前只支持数值型，应在写入时校验并文档化。
runtime_plan_override是运行时计划覆盖合理 用 (device, plan) 单行覆盖 op + body，能表达 add/update/delete 三态。语义够用， 但没有"覆盖历史"——出问题时无法回溯"这个计划被谁在运行时改成了什么"。
runtime_catalog_edit是运行时目录编辑合理 同 runtime_plan_override。注意 key 是列名——SQLite 里 key 不是保留字但容易与 meta.key 混淆，建议改名 entry_key。
runtime_host_report是主机动态报告合理 整块 JSON 存一行，用于重连后恢复 S2F33/35/37 定义的报告。粒度粗但符合"运行态可丢弃"的定位。
link_event1（仅测试）链路事件流水无界 只写不读（唯一读者是单测）。生产代码只在 Bootstrap 的相位回调里 appendLinkEvent，没有任何 API 暴露它。且没有保留策略—— cleanupOrphans 的清理列表里没有它，trim() 也不管它。 长期运行会无界增长。建议：要么补 GET /devices/{id}/link-events + 按天裁剪， 要么直接删表（相位变更已经有 SSE 推送）。
meta是元数据合理 与 config.db 的 meta 同构，只用于 schema 版本。

6.3 横向问题

维度现状建议
外键30 张表里只有 1 个外键（config_document → device）。 其余关系全靠应用层；而 device 只做软删，ON DELETE CASCADE 永远不会触发。 要么删掉这个外键（承认"应用层负责"），要么给投影/运行态表补上并改用硬删 + 归档。 半吊子状态最糟：让人以为有约束保护。
跨库一致性config.db 与 runtime.db 无事务关系，靠"启动对账"收敛。 updateConstants 写 config 后再单独写 runtime 追平 config_revision， 两步之间崩溃靠"启动一律拉回 STOPPED"兜底——这个取舍是正确且已文档化的。 保持。但要把 deviceKey 解析失败时的静默回退去掉（§2.3）， 否则"跨库不一致"会从"可预期的一类"变成"随机的一类"。
索引7 个显式索引，覆盖了主要查询。缺：plan_execution(device_id, status)、 host(name)、host_template(name)。 按查询补索引；link_event 若保留，需加 (entity, entity_id, at)。
保留策略config_revision 200 版 / plan_execution 5000 条 + 7 天 / 报文 16MB / 审计 8MB。link_event 无。 补 link_event；把保留参数提到配置（现在是 static final 常量）。
迁移只有"文件 → 库"的一次性迁移（ConfigMigrator，做得不错： 复制语义 + 自检 + 归档 + 幂等）。没有"库 schema 版本升级"机制。 见 §7 P0-3：加 migrations/V{n}.sql + 启动时按 meta.schema_version 顺序执行。
持久化分层三套：SQLite（配置/运行态/台账）、JSONL 文件（报文/审计）、 内存（报文 recent 环）。三套各有各的保留策略与查询方式。 这是合理的取舍（报文写入量太大不适合进 SQLite），但要在文档里明确 "哪些数据重启后还在、哪些不在"，目前只有代码注释里零散提到。

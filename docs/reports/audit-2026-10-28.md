## 1. 总体结论

**架构与工程底子是好的**：模块边界清楚，数据层统一收口，配置编译/校验只有一条路径，协议编解码的长度与深度防护到位，SSE 票据与断线补偿完整，593+108 个测试全绿。历史审核（10-17/10-20/10-25）提出的问题基本都已闭环。

**当前风险集中在四类**：

1. **协议层的连接生命周期缺陷**（P0-1）：被动端第二条 TCP 连接会把已选中链路注销，真机侧表现为"假掉线"，而主机侧仍以为 SELECTED。
2. **安全默认值**（P0-2）：server 形态默认 `0.0.0.0` + 无凭据 + `Access-Control-Allow-Origin: *`，而界面根本不支持凭据 —— 配了 token 反而不能用，等于把"必须开放"写死进产品。
3. **长任务与慢 I/O 挤占固定线程池**（P1）：压测请求在 4 线程的 HTTP 池里同步 `Thread.sleep`（最长 83 小时），报文日志在协议线程上同步 flush 三次，任一都会把整个 API/收发链路拖死。
4. **契约与文档漂移**（P2）：openapi 有 2 处重复键导致 2 个端点文档被静默丢弃、host-sims 全套端点未收录；打包脚本从 stderr 读 READY（实际写 stdout），打印的 API 地址是错的；版本号存在 2.0.0 / 2.0.0-SNAPSHOT 三处来源。

按严重度统计：**P0 2 项、P1 17 项、P2 30 项、P3 15 项**。

## 2. P0 —— 立即修（阻断/安全）

### P0-1 被动端任意第二条连接会注销已选中的 HSMS 链路

- 证据：
  - `secs-protocol/src/main/java/com/shimizukenta/secs/hsmsss/AbstractHsmsSsCommunicator.java:114-123`
    ```java
    protected boolean removeSelectedConnection(AbstractInnerConnection c) {
        synchronized (this.syncSelectedConnection) {
            if (this.selectedConnection == null) return false;
            this.selectedConnection = null;   // ← 完全不比对参数 c
            return true;
        }
    }
    ```
  - `secs-protocol/src/main/java/com/shimizukenta/secs/hsmsss/AbstractHsmsSsPassiveCommunicator.java:297-300`
    ```java
    finally {
        notifyHsmsSsCommunicateStateChange(HsmsSsCommunicateState.NOT_CONNECTED);
        removeSelectedConnection(this);       // ← 每个连接的 mainTask 都会执行
    }
    ```
- 现象：连接 A SELECT 成功 → 任意第二条 TCP（端口扫描、主机重连重叠、空闲探测连接）进来后未选中，10 秒 T7 超时或对端关闭 → 它自己的 `finally` 把 **A 的** `selectedConnection` 置空、并把全局 HSMS 状态改成 `NOT_CONNECTED`。此后 A 的 `send()` 抛 `NotConnected`、`communicatable()` 变 false，而 A 不会重新登记；主机侧仍是 SELECTED，只能靠新连接重新 SELECT。
- 影响：**真机联调中的"随机掉线/发送失败"**。被动端是多设备模拟器的常规形态（每会话一个监听端口），端口被扫描或主站重连抖动即可触发。
- 修法：`removeSelectedConnection` 先比对引用（`if (this.selectedConnection == c)`）；`finally` 只在本连接就是选中连接时才降级状态；`NOT_CONNECTED` 由"选中连接消失"派生，而不是由任意连接结束触发。
- 建议补测试：A 选中后，再建 B 连接并关闭，断言 A 仍可 `send`、状态仍 SELECTED。

### P0-2 server 形态默认对全网开放且无鉴权，界面又无法提供凭据

- 证据链（四处叠加）：
  1. `secs-runtime/.../RuntimeOptions.java:143`：`values.getOrDefault("bind", mode.loopbackOnly() ? "127.0.0.1" : "0.0.0.0")` —— server 默认绑所有网卡。
  2. `secs-runtime/.../Main.java:87-91`：缺凭据时只 `Log.warn`，继续启动；`resolveCredentials` 落到 `AccessControl.open()`（`Main.java:267-272`），匿名即 ADMIN。
  3. `secs-api-http/.../HttpApiServer.java:544-548`：所有路由回 `Access-Control-Allow-Origin: *`、放行全部方法与 `Authorization/Content-Type`。
  4. 前端从不发送 `Authorization`（`frontend/src/api.ts` 全文无 token 逻辑；`ConnectionPanel` 只编辑设备配置），`README.md:82` 自己承认"加了凭据后当前界面无法登录"。
- 影响：内网部署即等于**远程任何人可改配置、删会话、发报文、POST /shutdown**；且因为界面不支持凭据，运维为了能用只能退回开放访问。
- 另有两处一致性反证：`RuntimeOptions.usage():193` 写"server 模式必须显式给 --token 或 --auth-users"，代码只警告；`packaging/start-server.sh:32-34` 也不传凭据。
- 修法（最小改动即可显著收敛）：
  - server 缺凭据时**启动失败**（退出码 2），或要求显式 `--allow-open`；
  - 默认绑定改 `127.0.0.1`，对外绑定必须配凭据；
  - CORS 改为基于配置的来源白名单（同源托管时根本不需要 `*`）；
  - 界面补一个凭据输入（localStorage 保存，统一注入 `Authorization`；SSE 继续走票据）。

## 10. 真实主站复验与远程 TLS 自动化（2026-10-28 追加）

第 9 节的 P0-1 回归用的是裸 socket；本轮补两条更接近现场的自动化用例。

### 10.1 P0-1：用产品自己的主机栈复验

用例：`secs-cli/src/test/java/com/shimizukenta/secssim/cli/SessionSelectedLinkSurvivesRogueHostTest.java`

**角色是真实实现，不是桩**：
- 设备 = `HsmsSessionRuntime`（真实被动端、真实值引擎、真实 GEM 行为）；
- 主站 = 产品内置的 `HostSimulator`（真实 HSMS-SS ACTIVE + SELECT + SECS-II 事务），通过 `sendSml` 发 `S1F1 W.` / `S1F3 W.`；
- 干扰 = 第二条**真实 HSMS ACTIVE 连接**（`t5=0.3s`，被拒后持续重连），模拟"主机重连重叠 / 端口扫描 / 第二套上位机误连"。

**断言**：
1. 干扰连接存在期间 `device.hasPeer()` 仍为 true；
2. 干扰连接离开后 `device.hasPeer()` 仍为 true；
3. 主站 `S1F1 W.` 仍收到 S1F2（不超时）；
4. 主站 `S1F3 W.` 仍收到 S1F4（数据面无扰动）。

**证明用例不是空跑**：临时把被动端 `finally` 改回旧行为后运行，用例在断言 1 处失败
（`expected: <true> but was: <false>`）；恢复修复后通过。注意它在**干扰连接还在时**就失败：
rogue 每次被拒（ALREADY_USED）后会重连，旧代码把每一次断开都当成"选中连接结束"，
于是已选中的主站链路被反复注销——这正是现场"设备假掉线"的机制。

### 10.2 远程 + TLS + 账号文件：真实进程端到端

用例：`secs-runtime/src/test/java/com/shimizukenta/secssim/runtime/RemoteServerTlsAuthUsersTest.java`

不启动桩服务，而是用当前 JVM 的 classpath **真的拉起 `Main`**：

```
java -cp <test classpath> com.shimizukenta.secssim.runtime.Main \
  --mode=server --bind=127.0.0.1 --port=0 \
  --auth-users=<users.json> \
  --tls-keystore=<keytool 生成的自签 p12> --tls-password=changeit
```

客户端用 `https://127.0.0.1:<port>`（证书 SAN 同时含 `localhost` 与 `127.0.0.1`，信任策略仅本用例 trust-all）。覆盖：

| 场景 | 断言 |
|---|---|
| 启动握手 | 从 `<work-dir>/ready.txt` 取端口；stdout 不依赖 token |
| 匿名 health | 200 且**不含** `version`/`mode`（只回"活着"） |
| viewer health | 200 且含 `"role":"viewer"`、`"mode":"server"` |
| 无凭据 / 错口令 | `GET /sessions` → 401 |
| 角色矩阵 | viewer 读 200；viewer 停机 403；admin 停机 200 |
| 新收紧端点 | 匿名 `GET /host-sims` 401、viewer 200；匿名 `POST /config-preview` 401、operator 能进业务校验（非 401/403） |
| SSE 票据 | HTTPS 下 `POST /ticket`（viewer）换票 → `GET /events?ticket=…` 200，首帧 `: connected` |
| 审计 | 停机后 `logs/audit.jsonl` 含 `"actor":"owner"` 与 `"action":"shutdown"`，且 viewer 的 403 尝试也留痕（`"actor":"guest"`） |

这条用例同时验证了本轮整改的四处关键接线：**server 缺凭据拒绝启动**、**TLS 加载**、
**ready.txt 握手**、**账号文件驱动审计主体**——任何一处回退都会让它失败。

### 10.4 局限与现场抽验清单

- "真实主站"是产品自身的 HSMS/SECS 栈，**不是物理 EQP**。它比裸 socket 强（走完整
  SELECT、SystemBytes、W 位、S1F3 数据面），但仍不能替代现场联调。
- 建议现场按以下步骤抽验 15 分钟：
  1. 主站正常 SELECT，连续做 20 次 S1F1/S1F3，确认无超时；
  2. 在设备端口上另开一个 TCP 连接（或让主站软件"重复连接"一次），保持 10 秒后关闭；
  3. 观察设备日志**不应出现** `communicate state changed: NOT_CONNECTED`（主站仍在线时）；
  4. 回到主站继续 S1F1/S1F3，确认仍正常；
  5. 若现场有网络扫描/资产探针，确保扫描窗口内主站事务零 T3 超时。
- TLS 组合建议再手测一次"账号文件 + Windows 桌面壳（远程地址 + 令牌）"，覆盖本用例未涉及的 UI 路径。

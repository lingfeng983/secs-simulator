## 为什么这一条重要

自动发现型主机的启动流程是：

```
连上 → S1F13/S1F14 → S1F1/S1F2 → **S1F11/S1F12（你有哪些变量）** → 自己决定采哪些 SVID
```

没有 S1F12，这类主机在"枚举变量"这一步就停住，后面 S1F3/S6F11 全用不上。
而它恰好是纯查询、无副作用，实现成本最低。

## 交付

| 项 | 内容 |
|---|---|
| S1F11 → S1F12 | `<L[n] <U4 SVID>>` → `<L[n] <L[3] <U4 SVID> <A SVNAME> <A UNITS>>>` |
| 变量名规则 | 单元所属变量带单元前缀：`CH1_TEMP_PV`；设备级共享变量保持原名 |
| 单位 | 取 SVID 定义里的 `unitSymbol`（为此 `ResolvedSvid` 增加了该字段） |
| 空请求 | 返回**全部**变量（E5 允许的"枚举全部"用法，现场调试也常用） |
| 未知 SVID | 返回空字符串，但**行不能少**——主机按下标对位 |

## 两个刻意的选择

### 1. 变量名带单元前缀

两个腔体都有 `TEMP_PV`。若原样上报，主机侧看到两个同名变量却无法区分。
`CH1_TEMP_PV` / `CH2_TEMP_PV` 让名字本身带归属；设备级共享变量不加前缀。

### 2. 未知 SVID 不省略、不报错

E5 没有规定"未知 SVID 要不要跳过"。我们的选择是**保留行、填空串**：
主机普遍按下标与请求对位，少一行会让后面所有变量错位——那是灾难性的静默错误，
而空串至少是显式可查的。

## 明确未做：S2F33 / S2F35 / S2F37（主机动态定义报告）

这是协议支持里最后一个已知缺口，但我**没有**在这一批里做，原因是它不是一个"补个应答"的问题：

- `Gem` 只回 ACK 码（DRACK/LRACK/ERACK），**不保存**主机下发的 RPTID→VID、CEID→RPTID 定义；
- 要做对，会话必须维护一张**可变的动态报告表**，并决定：
  - 主机定义与本地 Schema v4 冲突时以谁为准？
  - 主机 `S2F33` 清空全部报告后，本地 S6F11 还能不能发？
  - `S2F37` 禁用 CEID 后，编排表里的事件是丢弃还是缓存？

这三个问题都是**产品语义**问题，不是编码问题；先写代码只会写出一个"看起来支持但行为随机"的实现。
它应该单独一批，并先写一条 ADR 定清优先级与冲突策略。

## 2. P0 —— 立即修

### P0-1 被动端 bind 失败被完全吞掉：会话报 `OPEN`，端口上其实没有监听

证据链（三处叠加）：

- `HsmsSsCommunicatorConfig.java:34`：`rebindIfPassive = 10.0F` 默认值 → PASSIVE 一律装 rebind 变体
  （`HsmsSsCommunicator.java:37-44`）；
- `AbstractHsmsSsRebindPassiveCommunicator.java:53-66,134-136`：bind 异常只交给 `notifyLog`，
  然后睡 10 秒重试，`open()` 正常返回；
- `HsmsConnector.java:47-50`：只注册 message/sent/state 三个监听器，**没有 `addSecsLogListener`**；
  `notifyLog` 无监听者即丢弃。全仓 grep 确认产品内**零处**注册过 `SecsLogListener`。

后果：端口被外部进程占用 → `open()` 成功 → `HsmsSessionRuntime.open` 置 `state=OPEN` →
界面显示设备健康、日志里一个字都没有，主机永远连不上。`RuntimeContext.createSession` 的
「端口绑定失败」分支对被动会话成为死代码。

修法（三件必须一起做，否则只是把「静默」换成「泄漏」）：

1. `HsmsConnector` 注册 `SecsLogListener`，把 bind/accepted/closed/reject/timeout 映射成会话级
   错误与诊断信息；
2. rebind 变体的**首次** bind 失败必须让 `open()` 抛错（后续重绑才静默重试）；
3. `AbstractHsmsSsPassiveCommunicator.open()` 在 `passiveOpen()` 失败时自回滚 `close()`
   （`super.open()` 已置 opened 并启动 5 条分发线程）。

### P0-2 无鉴权 + CORS 只挡「读响应」：本机 API 可被任意网页 CSRF，且 Host 未校验可被 DNS rebinding 绕过

`HttpApiServer.java:524-561`：

```java
String origin = allowedOrigin(ex);
if (origin != null) { /* 只加响应头 */ }
else if (OPTIONS) { 403; return; }
if (OPTIONS) { 204; return; }
try { handler.handle(ex); }      // ← 白名单之外的非预检请求照样执行
```

- 写端点全是**无正文的简单请求**（`POST /shutdown`、`/ceid/{n}`、`/alarm/{alid}`、`/reload`、
  `/host-sim`），不触发预检；任意网页一行 `fetch(...,{mode:'no-cors'})` 即可停机/触发上报。
- `allowedOrigin` 的同源比较用**请求里的 Host 头**（`HttpApiServer.java:580-585`），
  DNS rebinding 后 `Host`/`Origin` 都是攻击者域名 → 白名单成立且响应可读（可拉 `/messages`、`/audit`）。
- `packaging/start-server.sh:13-14` 默认 `BIND=0.0.0.0`，把「停机端点」直接暴露给整网。

修法：

1. 新增 Host 白名单（回环名/IP + `--bind` 的字面值 + 本机网卡地址 + 显式配置），不匹配一律 403；
   同源判定改用服务端已知的 bind/port，而不是请求头；
2. 非 `GET/HEAD/OPTIONS` 且带 `Origin` 的请求，Origin 不在白名单 → **403 且不执行 handler**；
   无 Origin（curl/脚本/桌面壳首跳）放行；
3. `start-server.sh` 的 `BIND` 默认回 `127.0.0.1`；非回环绑定时启动横幅打印风险提示，health 带 `exposed:true`。

## 3. P1 —— 两周内修

### P1-1 热重载后 S6F11 仍用旧设备模型组装

`HsmsSessionRuntime.java:350` 把 assembler **实例**注入 `EventReporter`（`EventReporter.java:26,87`
存为 `final`），而 `refreshModelViews`（`HsmsSessionRuntime.java:611-615`）只重建字段、不通知它。

触发：`reload` 的热生效分支（session 段不变，绝大多数配置改动）；界面「事件/报告/状态变量」运行时增删改。
后果：新增 CEID 触发时抛「未知 CEID」，事件永远发不出去；改 RPTID 的 VID 列表后报文结构与界面不一致
（值来自新模型、结构来自旧模型）。

修法：`EventReporter` 第一参数改 `Supplier<S6F11Assembler>`；补「reload 后 S6F11 的 RPTID 来自新模型」用例。

### P1-2 同端口「先开新再关旧」的重载路径不成立

`SessionLauncher.java:202-209`：`requirePortFree` 跳过自己，随后在旧监听 socket 还活着时 bind 同一端口。

- Linux：`SO_REUSEADDR` 不允许 LISTEN 重绑 → bind 失败 → 走 P0-1 的静默重试 → 接口回「重载成功」，
  设备最多 **10 秒无监听**；
- Windows：允许重绑 → 新旧监听器并存，切换窗口内的连接可能被即将关闭的旧实例接走再断链。

测试盲区：`reloadWithSessionChangeReplacesSession` 把端口从 4701 改成 4702，恰好绕开同端口路径。

修法：同端口重建改为「摘出注册表 → close 旧 → open 新」，open 失败用 `Prepared` 重开旧会话并回滚注册。

### P1-3 「选中链路」与「通信状态」不是原子派生（P0-1 修复后的残留竞态）

`AbstractHsmsSsPassiveCommunicator.java:293-303`：`removeSelectedConnection` 在锁内比对置空，
`notify(NOT_CONNECTED)` 在锁外。A 移除自己 → B 登记并发 SELECTED → A 回来发 NOT_CONNECTED，
于是 `selectedConnection == B` 但状态是 `NOT_CONNECTED`、`communicatable()==false`，且无路径重新派生。

修法：比对 + 置空 + 计算目标状态放进同一临界区，通知携带该结果；三处（passive/active/activeCircuit）统一。

### P1-4 半开连接永久 SELECTED：主机断电，设备仍显示在线

- `HsmsSsCommunicatorConfig.java:33`：`linktest = -1.0F`（默认关闭）；
- `AbstractHsmsSsCommunicator.java:806-810`：`-1` 时永久 `wait`，周期链路测试不跑；
- 首帧读 `readToBuffer(channel, lenBf, false)`（:648）与写（:604-623）都无超时；
- 产品侧 `HsmsConnector` 只设 t3/t5/t6，**从未调用 `config.linktest(...)`**。

后果：主机断电/拔网线（无 FIN）→ 读线程永久阻塞、状态永远 SELECTED、`send()` 把数据丢进内核缓冲
「成功」返回。界面显示 ONLINE，主机已死，没有任何错误与日志。

修法：`HsmsConnector` 显式开周期 linktest（30s 量级）+ 首帧读挂可配置空闲超时，超时按终止异常断链。

### P1-5 `Deselect.req` 永不应答（E37 违反）

`AbstractHsmsSsPassiveCommunicator.java:353-367,407-421`：`case DESELECT_REQ` 与 `default` 合并，
只做 supportSType/PType 判断；`createDeselectResponse` 全仓仅定义、零调用；主动端同样 ignore。

后果：对端等 T6 超时 → 判通信失败断 TCP；本端仍 SELECTED、继续应答 DATA。若主机反复重发，
设备永久卡在 SELECTED，新连接 `SELECT.req` 只能拿到 `ALREADY_USED`——现场表现为「必须重开会话才能连上」。

修法：`DESELECT_REQ` 单独分支 → 回 `Deselect.rsp` + 仅当本连接是选中连接时迁移到 NOT_SELECTED；
测试改为断言「收到 SType=4、状态 0」。注意与 NOT_SELECTED 的全局单值语义一起改。

### P1-6 值域约束缺失 + 编码期抛非受检异常

- `SvidDef.min/max/type` 只在 `DefaultCurves` 使用，用户写的 Step/Pwl/Constant 曲线完全绕过；
- `Secs2ValueOutOfRangeException extends IllegalArgumentException`，而 `innerSend`
  （`AbstractHsmsSsCommunicator.java:516-601`）只把 `Secs2BuildException` 包成 `SecsSendMessageException`。

后果：SVID 声明 U1、曲线输出 300 → 配置校验通过、设备启动成功、S1F3/S6F11 在发送线程抛异常，
事件丢失只留一行 `lastError`；手动 SML 的同类异常靠 `SessionHandler` 恰好 catch 了 IAE 才变成 400。

修法：`ValueSources.of` 出口包一层 `BoundedValueSource`（按 `ValueType` 宽度 clamp + NaN 归一 + 计数）；
`innerSend` 捕获 `Secs2ValueOutOfRangeException` 并包成 `HsmsSsSendMessageException`（该异常刻意是非受检的，
`bytes()` 的签名无法声明受检异常，因此不改继承而是补出口）；手动 SML 在**解析期**就按类型值域拒绝。

### P1-7 HTTP 请求池 4 线程 × 最长 45 秒阻塞（叠加慢正文可饿死整个 API）

- `HttpApiServer.java:59` `REQUEST_THREADS = 4`；T3 默认 **45 秒**（`SecsTimeout.t3`）；
- 手动 SML 带 W 同步等 T3；host-sim 建连最长 6s；配置草稿编译；`GET /messages?limit=5000` 序列化；
- `readBody` 无读超时：`Content-Length` 巨大 + 每秒 1 字节 → `readNBytes` 阻塞，关闭时 JDK 还会 drain。

4 个这样的请求即可让 health、轮询、SSE 取票全部排队，界面表现为「后端挂了」。

修法：慢路由挪独立有界执行器 + 每请求 deadline + `Content-Length` 预检（413）；中期换虚拟线程。

### P1-8 停机链没有关闭 host-sim 与 burst 执行器；`HostSimulator.close` 会漏关连接

- `Main.java:184-207` 的 cleanup 只有会话/probe/HTTP/两个日志；`RuntimeContext` 的 `hostSims`
  与 `burstExecutor` 无任何关闭入口（全仓无 `burstExecutor.shutdown`）；
- 关会话只清 `burstStates`，孤儿压测继续发最多 5 分钟，占死 2 个槽位；
- `HostSimulator.java:639-643,673-687`：发送失败先 `open=false`，`close()` 再用 CAS 包住
  `comm.close()` → CAS 失败则 communicator 既不关也不置 null，实例已被移出注册表，再没人能关。

修法：`RuntimeContext implements AutoCloseable` 接进 cleanup；`BurstState` 加取消；close 无条件关连接。

### P1-9 S2F15 常量落盘与界面保存配置互相覆盖

`ConfigStore.writeConstants:432-482` 与 `save:386-415` 都是「读原文 → 改一段 → 原子替换」，
**无互斥**；前者由协议线程在主机下发时调用。用户编辑器保存被静默覆盖，或反之；mtime 被改还会让下一次
保存莫名报「被其他操作修改过」。

修法：ConfigStore 加进程内锁；`writeConstants` 用 mtime 乐观检查，冲突回 S2F16=2 不落盘。

### P1-10 报警 S5F1 与采集 S6F11 共用同一个单线程 ACK 池

`HsmsSessionRuntime.java:294-295,350-363`：两者拿到同一个 `ackSender`（1 线程/队列 256）。
主机不回 S5F2 时，一条报警让后续 S6F11 的 W 位发送全部排队，队列满后成批 `wbitDropped`。

修法：报警用独立单线程执行器（与 `traceAckSender` 同构）。

### P1-11 预览曲线把「引擎 uptime」当墙钟打印

`previewWindow.ts:21-25` 用 `health().uptimeMs` 作右端点，`VariableChart.tsx:286-296,522-527`
却 `new Date(atMs)` → 状态变量预览的 X 轴显示 `00:02:00`（实为开机后 120 秒）；同一组件在主机采集页
传入的是 epoch，语义相反。值班时对不上报警时间。

修法：预览响应补 `baseEpochMs`，或前端由 uptime 推偏移；统一 `lib/format`。

## 6. 设计不合理（结构性）

1. **JSON 以字符串穿越分层**：`SessionRuntime` 返回 `alarmsJson/catalogJson/eventsJson/overviewJson/previewJson`
   文本；HTTP 层手拼并靠 `contains` 猜语义；`overviewJson` 用 `substring` 打补丁；两份相同的转义器。
2. **`SessionRuntime` 接口过宽**：`RuntimeContext.sessionsJson` 为多带一个 `config` 字段匿名重写 26 个方法；
   另有 40+ 个 `return false` 的 default 方法，调用方无法区分「不支持」与「不存在」。
3. **会话生命周期无单一 owner**：open/close/reload/register/端口检查分散三处，靠 launcher 全局锁维持；
   `reload` 的「先开后关」在被动端根本不成立。
4. **模型热替换靠手工通知**：`model/assembler/effectValues` 三个 volatile 各自发布，漏了 EventReporter。
5. **线程模型无登记**：HTTP 4 线程、SSE 每连接 1 线程、协议每连接 2–3 线程 + 无界 cached pool、
   每会话 4 个执行器、burst 池、host-sim 连接线程；没有一处能回答「进程有几个线程、怎么关」。
6. **路由手写**：`DELETE /sessions/{id}` 靠 `endsWith("/host-sim")` 区分，bulk 与前缀重叠靠注册顺序兜底。
7. **前端巨型 hook + 手写契约**：`api.ts` 1303 行、`useBackend` 925 行/49 字段，每次轮询产出新对象整树重渲染。

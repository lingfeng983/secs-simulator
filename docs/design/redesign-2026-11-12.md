# SECS Simulator 3.0 重新设计说明书

- 日期：2026-11-12
- 目标版本：3.0.0（相对当前 2.0.1 是一次**领域模型重构**，不是补丁）
- 输入需求：
  1. 设备的「关闭」不是直接删除，只是关闭连接；
  2. 主机的「断开」不是直接删除，只是关闭连接；
  3. 所有配置信息使用 SQLite 数据库进行管理；
  4. 设备详情页把「设备配置」与「运行态设备操作」区分开；
  5. 设备事件编排启用后，按计划发送消息，并且执行 SVID 的变化。
- **追加约束（2026-11-12 同日修订，覆盖初稿中「主机依附设备」的部分）**：
  6. **主机模拟与设备模拟完全不相关**：主机模拟的是 EAP / HOST 侧，可连接任意设备（本进程设备、外部设备、第三方模拟器），不与任何设备实体绑定；
  7. **主机实例可以单独多开**，数量与设备数量无关，实例之间互不影响；
  8. **页面只讲使用**：界面不出现数据库、持久化、表、事务、迁移、接口路径等技术实现词，也不放置与操作无关的说明、架构图或设计解释。
- **再修订（同日第二轮，覆盖追加约束里的「主机独立卡片工作台」形态）**：
  9. **主机模拟与设备模拟的展示方式保持一致**：两者都是「列表页 → 详情页（实例头 + 配置区 / 运行区 + 子页签）」，侧栏实例树、面包屑、状态徽标、按钮位置与配色一一对应；同构只作用于界面形态，两个领域的数据与生命周期仍然互不引用；
  10. **主机页面保留当前全部功能**：实例管理、消息发送、S6F1 Trace 采集、S1F3 数据采集、消息监控以及每台主机的控制台操作，一项不删，按「设置 / 操作」重新归位到两段式子页里。
- **第三轮修订（2026-11-13，评审追加，覆盖前两轮中侧栏与主机发送的形态）**：
  11. **侧栏三组**：左侧菜单固定三组——①「设备清单」（工作台入口 + 动态设备树）②「主机清单」（主机模拟列表入口 + 动态主机实例树）③「独立工具」（主机模板 / 设备模板 / 审计）；覆盖原型「总览 / 设备 / 主机 / 独立工具」四组形态；
  12. **主机实例模板**：预存「目标地址 / 端口 / Device ID / 采集配置」的模板（`host_template` 表 + `/api/v2/host-templates`），独立工具「主机模板」页管理；主机列表页新建时可从模板一键填入；
  13. **主机运行区严格单主机**：主机详情页「消息发送」只发本主机（无多选目标）；「收发记录」只看本主机，保留方向 / SxFy / 内容 / 类别过滤，并加「清理」按钮（按报文序号打水位，清理后仅显示更新的报文，新报文继续实时滚动）。

## 0. 现状结论（代码级核对，是本次设计的基线）

调查范围是全仓库 `src/main/java` 与 `frontend/src`，只读取证。基线是 2.0.1（`6107c35`）**加上尚未提交的在制改动**（每主机报文归属、每主机压测、消息监控页，见 §0.6）；本文行号以该工作树为准。在制改动必须先落地，本设计的文件索引（§6）已把它们计入必改范围。以下结论决定了改造的切入点。

### 0.1 需求 1 / 2：当前「关闭」确实等于「删除」

| 位置 | 现状 |
|---|---|
| `SessionManager.remove()` `secs-app/.../session/SessionManager.java:87-94` | `sessions.remove(id)` 先摘表，再 `removed.close()`；`ConcurrentMap<String, SessionRuntime>` 里再无该对象 |
| `SessionLauncher.close()` `secs-runtime/.../SessionLauncher.java:149-160` | 同时 `sources.remove(id)`，丢掉配置来源指纹、overrides、lastGood 回滚快照 |
| `RuntimeApi.closeSession()` `secs-runtime/.../RuntimeApi.java:363-370` | `bursts.cancel` + `hosts.closeAllOf(sessionId)` + `launcher.close`，级联销毁该设备全部主机实例 |
| `HostSimRegistry.closeById()` `secs-runtime/.../HostSimRegistry.java:136-149` | `hostSims.remove(hostId)` 再 `sim.close()`；`jsonById()` 之后返回 404 |
| `HostSimulator.stateJson()` `.../hostsim/HostSimulator.java:815-828` | 没有「已断开」这一实例状态；断开 = 实例从注册表消失 |
| `SessionRuntime` 接口 `secs-app/.../session/SessionRuntime.java:20-101` | 现有 `id() / open() / close() / state() / lastError() / deviceName() / configName() / hasPeer() / controlState() / hostTarget()`，**没有** disconnect / reconnect / linkPhase |
| `HsmsSessionRuntime.close()` `.../session/HsmsSessionRuntime.java:851-881` | 停 ticker、三个 ACK 线程池 `shutdownNow()`、`comm.close()`、`communicator=null`、`state=CLOSED`；对象仍可被 GC |
| 唯一近似能力 | `HostSimulator.reconnect()` `:245-261` 保留实例换连接，但语义是「断开后立即重连」，没有「停在断开态等手动重连」 |

补充事实：SSE 现有帧为 `NoticeEvent.java:18-24` 的 `s6f11 / alarm / session` 三类，加上独立发布的 `message`（`StreamHandler.java:190`）与 `heartbeat`（`StreamHandler.java:316`），**没有链路生命周期事件**，前端只能靠 `refreshSessions()` / `refresh()` 轮询感知消失；`DELETE /api/v1/sessions/{id}` 与 `DELETE /api/v1/host-sims/{id}` 的语义在 README 里也写成「关闭并移除会话」「断开实例」。

### 0.2 需求 3：当前配置全在文件与内存，且分散在 7 处

| 配置数据 | 现在的位置 | 持久化 |
|---|---|---|
| 设备配置原文 | `<work-dir>/*.json`，`ConfigStore` 读写 | 是 |
| 自定义模板 | `<work-dir>/templates/<id>.json`，`TemplateStore` | 是（但 `save()` 是**非原子、无锁**的直接 `Files.writeString`，`TemplateStore.java:138`） |
| 内置模板 | `DeviceTemplates.java` / `ConfigTemplate.java` 的 Java 字符串常量 | 编译期 |
| 内置演示配置 | classpath `/defaults/demo-*.json` 播种到 work-dir | 是 |
| 设备常量 ECV | 配置 JSON 的 `equipment.constants[]`，S2F15 由 `ConfigStore.writeConstants()` 原子写回 | 是（唯一会写盘的运行时数据） |
| 模板归属标记 `template` | 配置文件顶层键 | 是 |
| 运行时编辑 / 钉值 / 主机动态报告 / 部署覆盖 | `RuntimeCatalog`、`EffectValueSource.pinned`、`HostReportTable`、`SessionOverrides`、`SessionLauncher.sources` | **否，全内存，重载即丢** |

并发控制是「进程内 `ConfigStore.FILE_LOCK` + 跨进程 `modifiedMs` / `If-Match` 乐观锁」（`ConfigHandler.java:424-434`、`api/configs.ts:102-123`）。`--config <path>` 是唯一能加载 work-dir 之外配置的入口，不受 `requireFileName` 约束。

**与既有决策冲突**：ADR 0015 §4「SQLite：不做」的理由是「sqlite-jdbc 带来 JNI，直接破坏单文件原生镜像」。本设计需要**显式取代该结论**，见 §2.3 与 ADR 0017。

### 0.3 需求 4：当前设备页 10 个子页混在一起

`frontend/src/app/router.ts:31-33` 的 `DEVICE_PAGES` 是扁平的（`DevicePage.tsx:16` 只是导入它）：
`ceids / reports / events / alarms / svids / connection / structure / config / send / messages`。

- `connection`、`structure`、`config` 改的是**磁盘配置**；
- `events`（启停/触发/运行时增删改）、`alarms`、`svids`（钉值）、`send`、`messages` 改的是**运行中会话内存**；
- `CeidPanel` / `SvidPanel` 的说明自己也写着「这些改动只作用于当前会话，不写回配置文件；重载后按配置恢复」。

扁平页签 + 同一套「保存」按钮，让「改定义」和「改运行态」在视觉上无法区分。另外 `DevicePage.tsx:118-135` 在会话不存在时直接显示「会话 X 不存在，它可能已被关闭」——这正是需求 1 要消除的体验。

设备子页之外还有两个**全局页**（`navigation.ts:59-79`）：「模板管理」`#/templates`（`TemplatePage`，设备模板增删改查，工作台新建设备只从这里选模板）与「审计」`#/system/audit`。两者与本次分区无关，**原样保留**，只把数据源从 `TemplateStore` 换成 `device_template` 表。侧栏「主机模拟」的说明文案 `navigation.ts:53` 现在写着「各自选本机设备或远程 SECS」，违反需求 8，必须一并改。

### 0.4 需求 5：功能已闭环，但缺「可编排的消息」「执行台账」「持久化启用态」

**必须澄清**：当前 2.0.1 已经实现了「周期触发 → 发 S6F11 → 施加 EventEffect → 报文体读到新值」：

- 驱动：`EventTicker` 100ms（`.../session/EventTicker.java:36-48`）→ `pumpNow()` → `EventScheduler.pumpEvents()`；
- 触发：`EventSchedule.between()` 的 `At / Periodic`，`pumpConditions()` 的 `OnCondition`，`pumpPending()` 的 `AfterEvent`；
- 发送：`EventReporter.emit()` `:130-185`，`comm.send(6, 11, wbit, body)`；
- 改值：`applyPlanEffects()` `:217-237` → `EventEffectStore.apply()`，`EffectValueSource` 叠加 `set/add/shift/pulse/resume`；
- **先 apply（`:142`）后 build（`:147`）**，所以 S6F11 报文体已含变化后的值，S1F4 / S6F1 / Trace / 预览都读同一个 `ValueSourceHandle`（`HsmsSessionRuntime.java:268-272` 装配 `EffectValueSource`，`:362-366` 装配的 `SvidReader` 同源取值）。

真正的缺口是：

| 编号 | 缺口 | 证据 |
|---|---|---|
| G1 | `Fire(atMs, planId, ceid)` 与 `EventPlan(id, ceid, trigger, effects)` **没有 message 字段**，消息类型被写死为 S6F11、报文体被写死为 CEID 绑定的报告；无法按计划发 S5F1 / S10F1 / 任意 SML | `Fire.java:10`、`EventPlan.java:14`、`EventReporter.java:147-176` |
| G2 | 草稿预览 `POST /config-preview` 调用 `EventSimulator.simulate()`，返回值只含事件标记（内部虽走 `simulateWithEffects` 做条件求值，效果层不带回、也不作用到会话），曲线仍用基线 `values`；与会话预览 `simulateWithEffects()` 展示的叠加效果不一致 | `EventSimulator.java:78-81`、`RuntimeApi.java:435-443`、`svid-value-model.md:263-269` |
| G3 | 启用/禁用是纯内存 `disabledPlans` 集合，重载或重启即丢；没有「启用后从何时起算」「下一次触发时间」「本次执行结果」 | `EventScheduler.java:73-74, 246-282`、ADR 0011 |
| G4 | 运行时新增/修改计划只校验 CEID，**不校验 effect 的 SVID 存在性与类型**，写错会静默无效 | `EventScheduler.java:295-333` |
| G5 | 效果在发送之前落库，发送失败也改值；没有「执行成功/失败」的台账，现场无法回答「这条计划到底发没发、SVID 变成多少」 | `EventReporter.java:142-176` |
| G6 | 效果靠 `planId` 回查实时编排表，理论上存在「事件发了、值不动」的路径（2.0.1 已用实时表缓解，但仍有兜底告警） | `EventReporter.java:232-236` |
| G7 | 无主机在线时心跳只推进 `lastFireMs` 并 `resetConditions()`、清空 `pendingFires`（`EventScheduler.java:374-382`），不积压、不补发（ADR 0005 决策，Spooling 未实现），「启用后按计划发送」在离线期间表现为静默跳过 | `EventScheduler.java:374-382` |

### 0.5 追加需求 6 / 7：当前主机模拟是「设备会话的附属物」

初稿只把「断开 = 删除」当成主机侧的问题，遗漏了更根本的绑定关系。代码级复核结论：

| 位置 | 现状 |
|---|---|
| `HostSimHandler.java:53-91` | `POST /api/v1/host-sims` 请求体 `session` **必填**，缺失回 `400 missing-session`；字段名是 `session` 而非 `sessionId`。旧端点 `POST /api/v1/sessions/{id}/host-sim`（`SessionHandler.java:466-502`）把绑定写进 URL |
| `HostSimRegistry.open()` `:50-62` | `sessionId` 必填且必须 `sessions.find(sessionId)` 命中，否则 `UNKNOWN_SESSION`；没有「不绑定会话」的创建入口 |
| `HostSimRegistry.java:36-43` | `hostsBySession: ConcurrentMap<String, List<String>>` 反向索引，主机实例按设备会话分组存放 |
| `HostSimulator.java:84-95` | 实例持有 `sessionId` 字符串，本机模式还持有从设备派生的 `ResolvedEquipment localModel` |
| `HostSimulator.doOpen()` `:179-207` | 本机模式目标取 `runtime.hostTarget()`（即设备会话监听的 `bindHost:port`），远程模式才用请求体的 `host/port/deviceId`；两者都走 TCP `HsmsSsCommunicator` ACTIVE，**不存在进程内直连** |
| `HostSimRegistry.closeAllOf()` `:391-403` | 删除会话时把该会话登记的全部主机实例 `remove + close()`，即级联销毁；`RuntimeApi.closeSession()` `:363-370` 显式调用它 |
| `HostSimRegistry.java:91-104` | 「一台设备只允许一个本机主机」硬约束：遍历该会话已有实例，有任一 `isOpen()` 就回 `CONFLICT`；前端 `HostTargetPicker.tsx:31-34, 67-103` 同步把已占用设备置灰 |
| `HostSimRegistry.hostIdOf()` `:169-182` | 全部 `xxxBySession` 方法只取列表里**最后一个仍登记**的实例（并顺带清理失效 id），所谓「多主机」在会话级接口上形同虚设 |
| `HostTargetPicker.tsx:111-221` | 新建表单强制选设备；远程弹窗也必须带「宿主会话」，并提示「无，先在左侧选一台本机设备」 |

**结论**：主机实例没有独立身份，创建、寻址、模型、生命周期、数量上限全部由设备会话决定。追加需求 6 / 7 要的是一次**领域解耦**，而不是给现有 `closeById()` 换个名字。§2.2.1、§2.4、§2.5、§3 已据此改写。

### 0.6 在制改动与身份现状（同样属于基线）

**在制改动（33 文件，+1228/−364，尚未提交）做的是「每主机可观测性 + 每主机压测」，不是解耦**：

| 改动 | 位置 | 对本设计的影响 |
|---|---|---|
| `MessageEvent` 增加 `hostId`、`ofHost()` 工厂 | `secs-app/.../event/MessageEvent.java:16-17` | 是 §2.4.2 每主机报文归属的基础，保留 |
| `MessageLog` 落盘 `hostId`、SSE 帧带 `hostId` | `MessageLog.java:480,539,565`、`StreamHandler.java:192` | 但 `MessageLog.select():504-533` **仍无 hostId 过滤参数**，`GET /hosts/{id}/messages` 需要新增 |
| 每主机压测 `POST /host-sims/{id}/burst` | `HostSimHandler.java:214-242`、`BurstRunner.java:239`、`ApiContext.java:609` | 能力保留，路径迁到 `/hosts/{id}/burst` |
| 新增消息监控页 | `router.ts` 的 `HOSTSIM_PAGES` 增 `monitor`、`HostSimMonitorPanel.tsx`、`shared/lib/hostMessages.ts` | 归位到主机运行区「收发记录」 |
| **本机报文归属假设「一设备一主机」** | `hostMessages.ts:35-53` 构造 `localHostBySession: Map<session, 单个 hostId>` | **与需求 7 正面冲突**，多开必须重写归属逻辑，见 §2.4.2 |
| 本机模式不发布主机侧报文 | `HostSimulator.installPassThrough():270-277` 以 `!isRemote()` 提前返回 | 解耦后必须对所有主机开启，并解决与设备侧重复计数的问题 |
| 监控页文案含实现词 | `HostSimMonitorPanel.tsx:214-215` 显示 `logs/messages.jsonl` 与 `hostId` | 违反需求 8，纳入 §3.5 清理 |

这批改动**不满足需求 1/2/6/7 中任何一条**：`closeById()` 仍是先摘表再关闭，`RuntimeApi.closeSession():368` 的 `hosts.closeAllOf()` 级联仍在，`sessionId` / `localModel` / `hostsBySession` / 唯一性检查全部保留。

**身份现状（决定迁移与 v1 兼容）**：

- `sessionId` **就是配置文件名 stem**：`DeviceTemplates.deriveId():96-104` 去掉 `.json`，`ConfigStore.createFromTemplateText():364-394` 反过来把 `session.id`（`:381-383`）与 `equipment.name`（`:391-393`）强制改写成 stem；`requireFileName():607-624` 要求 `.json` 后缀并禁止 `/ \ .. :`。v1 的 `/sessions/{id}`、前端深链 `#/device/{id}`、CLI 脚本、`--config` 全部依赖这个 stem。
- 主机 id 是**进程内计数器** `"host-" + hostSeq.incrementAndGet()`（`HostSimRegistry.java:63-65`），不持久化，重启即变。
- 因此 §2.2.1 的 `device.id` 换成 ULID 时**必须保留 legacy 别名列**，§2.3.3 的迁移必须建立映射，主机 id 必须改为持久稳定 id。

## 1. 总体原则与需求映射

| 原则 | 说明 |
|---|---|
| **P1 定义与运行分离** | 「设备 / 主机」是**持久实体**（在 SQLite 里），「连接 / 会话」是**可开可关的运行态**。删除实体必须是一个独立的、显式的、带二次确认的动作 |
| **P2 单一事实源** | 配置只认 SQLite：`config.db` 里的原始 JSON 文档是唯一权威正文；结构化表是**由文档重算的投影**，不是第二份真相 |
| **P3 双库物理隔离** | `config.db`（可备份、可迁移、有版本历史）与 `runtime.db`（可随时丢弃重建）分开，避免「运行态脏数据污染配置」，也把需求 4 的分层落到后端 |
| **P4 事件即事务** | 一次计划触发 = 一条执行台账记录，包含「施加了哪些 SVID 变化」+「发了哪些报文」，前后顺序固定、结果可查 |
| **P5 保持四条铁律** | `secs-protocol` 仍只依赖 JDK 且冻结；不用 `--enable-preview`；曲线仍是时间纯函数；模板图仍是纯函数 DAG。本次改动不触碰 `secs-protocol` |
| **P6 主机是独立域（追加需求 6/7）** | 主机实体**不持有** `deviceId` / `sessionId`，**不依赖**设备模型，**不随**设备生命周期变化；连接目标只是一个 HSMS 地址。主机数量与设备数量无关，实例之间互不影响，多台主机可配置同一目标或不同目标 |
| **P7 界面只讲使用（追加需求 8）** | 存储、接口、模块、实现类等信息只存在于后端文档与 ADR，不进入产品界面；界面也不提供「设计说明 / 架构图」类页面 |
| **P8 两个域同构但不相交（追加需求 9/10）** | 设备与主机共用同一套界面骨架与交互语言（列表 → 实例头 → 配置区 / 运行区 → 子页签），但各自读自己的数据、走自己的接口；「长得一样」不等于「互相引用」。主机现有功能一项不删，只按配置 / 操作重新归位 |

```sql

  device_id TEXT PRIMARY KEY,            -- 无跨库外键，靠 id 关联

  message_json TEXT NOT NULL DEFAULT '[]', -- [{kind,stream,function,wbit,sml,sentAt,elapsedMs,ack}]
  effect_json  TEXT NOT NULL DEFAULT '[]', -- [{svid,op,before,after,detail}]
  error TEXT NOT NULL DEFAULT ''
);
CREATE INDEX idx_exec_time ON plan_execution(device_id, fired_at DESC);
CREATE INDEX idx_exec_plan ON plan_execution(device_id, plan_id, fired_at DESC);
-- 预览（EventSimulator / config-preview）一律不写台账，只在内存里产出结果

CREATE TABLE runtime_svid_pin (
  device_id TEXT NOT NULL, svid INTEGER NOT NULL, value REAL NOT NULL,
  set_at INTEGER NOT NULL, PRIMARY KEY (device_id, svid)
);
-- 运行时新增/修改/删除的计划正文（现有 EventScheduler.addEventPlan/updateEventPlan 只改内存）
-- 只存正文与操作标记，启用态与计数仍在 runtime_plan_state；reload 时整表清空，回到 config.db 的定义
CREATE TABLE runtime_plan_override (
  device_id TEXT NOT NULL, plan_id TEXT NOT NULL,
  op TEXT NOT NULL CHECK (op IN ('add','update','delete')),
  body_json TEXT NOT NULL DEFAULT '{}',  -- op=delete 时为空
  updated_at INTEGER NOT NULL, PRIMARY KEY (device_id, plan_id)
);
-- 运行时对 CEID / 报告 / SVID 目录的临时增删改（现有 RuntimeCatalog，「不写回配置文件」）
CREATE TABLE runtime_catalog_edit (
  device_id TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('ceid','report','svid')),
  key INTEGER NOT NULL,                  -- ceid / rptid / svid
  op TEXT NOT NULL CHECK (op IN ('add','update','delete')),
  body_json TEXT NOT NULL DEFAULT '{}',
  updated_at INTEGER NOT NULL, PRIMARY KEY (device_id, kind, key)
);
-- 主机动态报告：payload_json 明确为 HostReportTable 的完整序列化
-- {reports:[{rptid,svids}], links:[{ceid,rptids}], enabledCeids:[...], allEnabled:bool}
-- 必须含 S2F37 的启用态，否则重连后「停用的事件」会自己复活
CREATE TABLE runtime_host_report (
  device_id TEXT NOT NULL, payload_json TEXT NOT NULL, updated_at INTEGER NOT NULL,
  PRIMARY KEY (device_id)
);
CREATE TABLE link_event (
  id INTEGER PRIMARY KEY AUTOINCREMENT, entity TEXT NOT NULL, entity_id TEXT NOT NULL,
  from_phase TEXT, to_phase TEXT NOT NULL, at INTEGER NOT NULL, detail TEXT NOT NULL DEFAULT ''
);
-- 刻意不持久化：EventEffectStore 的效果叠加层（每 SVID 64 条 FIFO、pulse/decay 是时间函数）。
-- 它与「曲线是时间纯函数」的铁律冲突，重连后按当前时刻重新计算，不回放历史效果。
-- 因此 §2.4.1 的「原样恢复」只覆盖上面四张表，不覆盖已施加的效果。
```

**为什么是两个库**：`config.db` 要被备份 / 迁移 / 版本比对，`runtime.db` 每 100ms 可能写执行台账。混在一个文件里会让「备份配置」顺带备份一堆运行垃圾，也会让 WAL 检查点与配置写事务互相拖。跨库不做事务，靠 `device_id` 弱关联；任何跨库一致性用「启动时对账」补偿（§2.4.4）。

### 2.3 存储实现、并发与迁移

#### 2.3.1 JDBC 与原生镜像（取代 ADR 0015 §4）

| 方案 | 结论 |
|---|---|
| **A（推荐）** `org.xerial:sqlite-jdbc`（3.47+），WAL + `busy_timeout` + 单写者 | 保留单文件原生 exe。代价：JNI，需要 GraalVM 侧适配 |
| B 放弃 integrated 原生镜像，改发「瘦 JRE + jar」 | 丢掉「无需 JVM」的卖点。**注意这不是现成兜底**：现有 Linux 包发 7 个 jar 且启动脚本要求目标机已装 JDK 25+，Windows 根本没有 jar 路径，仓库里没有 jlink / jpackage。选 B 等于新开一条打包工作流 |
| C 纯 Java 引擎（H2 等）伪装 SQLite 文件 | **拒绝**：不满足「SQLite 数据库」的字面要求，且没有 `.db` 互通性 |

**前置现状（必须先补齐，否则方案 A 的清单是空中楼阁）**：

| 项 | 现状 |
|---|---|

**M0 尖峰（先于 M1，不通过则不启动存储改造）**：

1. 只做一件事——原生 exe 内 `SELECT sqlite_version()` + 建 `config.db` / `runtime.db` + 写一次 `plan_execution`，Windows 与 Linux **双平台**跑通；
2. 从零创建 `reachability-metadata.json`：注册 `org.sqlite.JDBC` 反射与 `org/sqlite/native/.*` 资源；把 `-H:IncludeResources` 从 `defaults/.*` 扩到含该路径；
3. `sqlite-jdbc` 的 native lib 不能从镜像内部 `dlopen`：启动时由 `DbBootstrap` 把 `org/sqlite/native/{Windows|x86_64,Linux|x86_64}` 下的库释放到 `<work-dir>/native/`，再设 `-Dorg.sqlite.lib.path`。需验证 work-dir 只读、被杀软拦截、位于网络盘三种场景的失败提示；
4. `native-nightly.yml` 改为**失败即红**（去掉 `continue-on-error`）并补 Linux job；`NativeRuntimeIT` 增加上述 DB 断言；
5. `scripts/package-windows.ps1` / `package-linux.ps1` 把对应平台 `.dll` / `.so` 作为外部文件随包发布（镜像内仍带一份用于自释放）；
6. M0 失败且短期无法修复 → 走方案 B，但必须把「新建瘦 JRE 打包链路」当成独立工作项排期，并在发版说明中声明形态变化。

> 说明：ADR 0015 反对的是「为了日志引入 JNI 不划算」。本设计把 SQLite 用于**配置与执行台账**（需要事务、版本、并发读、结构化查询），收益与日志完全不同，因此 ADR 0017 明确取代其 §4，其余三项（不做 Jetty / 不做签名 / 不做 Spooling）继续有效。但 ADR 0015 对「JNI 破坏单文件镜像」的技术判断本身成立，所以 M0 是硬门禁而不是形式步骤。

#### 2.3.2 `ConfigRepository` 的写路径（唯一写口）

```
saveDocument(deviceId, body, expectedRevision, actor, note)
  ├─ ConfigStore.validate(body)                    // 复用现有判据：parse → compile → buildValues
  ├─ BEGIN IMMEDIATE
  │    ├─ SELECT revision FROM config_document WHERE device_id=?   // 乐观锁
  │    ├─ revision+1 → UPDATE config_document
  │    ├─ INSERT config_revision(revision+1, 新正文快照)   // 版本历史从迁移播种的 revision 1 起连续完整
  │    ├─ DELETE 该 device 的全部投影行 → reproject(body) → INSERT
  │    └─ COMMIT（任一步失败整体 ROLLBACK）
  └─ 发布 SSE config-changed(deviceId, revision)
```

- 纯文本编辑：`body` 逐字节写入（保留未知键 / 空格 / 缩进）；结构化编辑：`JsonHub` 只改目标子树后整体 pretty print（**与现有 README 已声明的行为一致**：结构化编辑重排成 2 空格、未知键保留），然后走同一个 `saveDocument`。
- **两类写者必须分开**，否则现场每写一次设备常量就永久挂一条「配置待生效」：

  | 写者 | 入口 | revision | `config_revision` 快照 | `device_link.config_revision` | 漂移横幅 |
  |---|---|---|---|---|---|
  | 使用者编辑（界面保存 / 结构化编辑 / 回滚 / 迁移） | `saveDocument` | +1 | 写 | 不动 | 出现，需 `reload` |
  | 运行态回写（S2F15 ECV） | `updateConstants` | +1 | **不写** | **提交后立即追平** | **不出现** |

  理由：ECV 在事务成功后立即改内存、已经生效，运行版本本来就等于最新版本。若沿用 `saveDocument` 的语义，横幅会永久挂着，而使用者点「重载」会清空钉值与运行态编辑——把一个正常的 SECS 交互变成「必须做破坏性操作才能消除的告警」。同时避免高频 S2F15 撑爆版本历史。
- `updateConstants(deviceId, Map)` 落地：config.db 事务里替换 `body.equipment.constants` + 升 revision + 重投影（**不写版本快照**），提交后立即在 runtime.db 里 `UPDATE device_link.config_revision`（两库不做跨库事务，见 §2.2.2；两步之间崩溃无害——启动对账一律把设备拉回 STOPPED，重连按最新正文重建运行态，天然无漂移），最后才改 `ConstantStore` 内存；任一步失败仍回 `EAC=2`（保持 `HostCommandHandler.java:400-416` 的「先落盘再改内存」语义，只把「盘」从 JSON 文件换成 SQLite 事务）。ECV 是设备侧权威写入，**不因使用者正在编辑而失败**：只替换 `constants` 子树，其余正文按当前值保留。
- **在线备份用 `VACUUM INTO`**（或 sqlite backup API），不能直接复制 `config.db`——WAL 下未检查点的数据会丢。`--export-config` 导回 JSON 是跨版本回滚通道，两者并存。
- `Db` 内部单写者：`ReentrantLock` + 一个专用虚拟线程串行执行写事务；读用独立连接（`SQLiteDataSource`），WAL 下读写不互锁。
- 跨进程：与现有日志的约束一致——**同一个 `--work-dir` 不允许跑两个进程**；启动时对 `config.db` 加文件锁，抢不到直接失败并给出明确提示。
- `modifiedMs` / `If-Match: <ms>` → `If-Revision: <n>`；`ConfigHandler`、`api/configs.ts:102-123` 同步改。

#### 2.3.3 迁移（一次性，可回滚）

启动参数新增 `--migrate-config`（默认在检测到 `config.db` 不存在且 work-dir 有 `*.json` 时自动执行）：

1. 依次导入 `<work-dir>/*.json`（跳过 `legacy/`）→ `device(id=新 ULID, legacy_id=文件名 stem, name=stem)` + `config_document(revision=1)` + `config_revision` + 投影。**`legacy_id` 是 v1 别名与旧深链的唯一解析依据**（现状 `sessionId` 就是 stem，见 §0.6），必须落库；
2. 导入 `<work-dir>/templates/*.json` → `device_template(source='custom')`；
3. 播种 4 个内置模板 → `device_template(source='builtin', readonly=1)`；
4. 播种 classpath `/defaults/demo-*.json`（若目标尚无同名设备）；
5. `--config <path>` 外部文件：作为一台设备的初始正文导入，`meta.migration_source` 记下原绝对路径（外部文件不移动、只记录来源）；
6. 提供 `--export-config <dir>` 把全部设备导回 JSON 文件（回滚通道），文件名用 `legacy_id`，保证导回后与 `legacy/` 原文一致；
7. 主机实例：现有 `host-N` 是进程内计数器、不持久化，**没有可迁移的主机数据**；迁移后新建主机一律用持久 `host_01J...`。若 work-dir 里有历史主机导出文件，按 `name + target_host + target_port` 去重导入；
8. 迁移自检（在动原文件之前执行）：设备数与正文 SHA256 逐一比对、`legacy_id` 无重复、`name` 在未删除行内唯一；
9. **自检全部通过后才归档**：把已导入的原文件**移动**到 `<work-dir>/legacy/`（不删除）并写 `meta.migration_source='files@2026-11-12'`。任一自检项不过则整体回滚——DB 回滚、原文件原地不动，work-dir 仍可用 2.x 方式启动，下次启动重新迁移。导入全程是复制语义，移动只发生在最后一步，杜绝「迁移半途失败、JSON 已被搬走」的空窗。

迁移是幂等的：以 `content_sha256` 判重；中断后重启继续。

### 2.4 两条互不耦合的生命周期：关闭 = 断链

#### 2.4.1 两层状态机

**设备实体**（`config.db.device`）只有 `存在 / 软删除` 两态，与连接无关。
**设备链路**（`runtime.db.device_link`）：

```
  STOPPED ──connect()──→ STARTING ──ok──→ LISTENING ──对端 select──→ CONNECTED
                            │               │                         │
                            │ fail          │ disconnect()            │ disconnect() / 对端断开
                            ▼               ▼                         ▼
                          FAILED        DISCONNECTED ←────────────────┘
                            │               │
                            └──connect()────┴──connect()──→ STARTING（复用同一对象）
```

- 动词与 API 一致：`connect / disconnect / reconnect`（`reconnect()` 是「对已存在对象再 `connect()`」的别名）。**`delete()` 不是相位迁移**，它是实体动作：只在 `STOPPED / DISCONNECTED / FAILED` 下允许，链路仍 up 时回 `409 link-still-up`；成功后在 config.db **一个事务**里置 `deleted_at` 并删除 `config_document` / `config_revision` / 全部投影行（正文与版本历史真的消失，与删除确认弹窗列出的清单一致），`device` 表只留墓碑（id / name / 时间，供审计与改名复用）；runtime.db 侧的 `device_link` 与五张运行态表、执行台账不做跨库事务，由启动对账按「device_id 不在 live 设备集」统一清理（§2.4.4）。
- `LISTENING`：passive 端口已绑定、尚无主机 select；`CONNECTED`：HSMS selected。**`LISTENING` 必须有 `disconnect()` 边**——「设备已启动但主机还没接进来」是最常见的关闭场景，此时同样要释放端口。`controlState` 仍按 `OFFLINE / COMMUNICATING / ONLINE` 单独维护（E5 简化模型，不改）。
- **主动模式（`passive=0`）的设备没有 `LISTENING`**：现有 `HsmsConnector.java:66` 按 `spec.passive()` 切换 PASSIVE/ACTIVE，主动设备 `STARTING` 后直接向目标发起 TCP 连接与 Select，成功即 `CONNECTED`，失败进 `FAILED`。`requirePortFree()` 只对被动会话生效（`SessionLauncher.java:424-445`），主动设备的端口占用检查不适用。
- `DISCONNECTED` 与 `STOPPED` 的区别：`DISCONNECTED` 保留 `runtime_svid_pin` / `runtime_plan_state` / `runtime_plan_override` / `runtime_catalog_edit` / `runtime_host_report`，重连后恢复；`STOPPED` 是进程启动后的初始态，无保留内容。
- **「原样恢复」的边界**：恢复的是上面五张表的内容（钉值、计划启用态与计数、运行时计划正文、运行时 CEID/报告/SVID 编辑、主机动态报告含 S2F37 启用态）。**已施加的效果叠加层不恢复**——`EventEffectStore` 是每 SVID 64 条 FIFO 的时间函数，与「曲线是时间纯函数」铁律冲突，重连后按当前时刻重新计算。界面文案对应写「重新连接后恢复手动设定与计划开关」，不承诺恢复历史跳变。
- **「重载」定义**：以当前 `config_document` 重建运行态 → 清空三张运行态编辑表 → 若 `connection_spec` 指纹未变走 `applyHot()`（不断链），否则 `disconnect() + reconnect()`。重载后 `config_revision` 与运行一致。

**主机链路**（`runtime.db.host_link`）是**与上图完全平行的第二条状态机**，两条状态机之间没有任何边：

```
  DISCONNECTED ──connect()──→ CONNECTING ──ok──→ CONNECTED
        ▲                          │                │
        │                          │ fail           │ disconnect() / 对端断开
        │                          ▼                │
        │                        FAILED             │
        │                          │                │
        │                          └─connect()─→ CONNECTING（重试边，回到上方）
        │                                           │
        └──────────────disconnect()◄────────────────┘
```

（`FAILED` 有两条出边：`connect()` 回 `CONNECTING`——使用者点击或 `auto_reconnect=1` 的退避定时器；`disconnect()` 清错误回 `DISCONNECTED`。）

| 当前相位 | 动作 | 下一相位 | 说明 |
|---|---|---|---|
| `DISCONNECTED` | `connect()` | `CONNECTING` | 唯一入口，不查询任何设备 |
| `CONNECTING` | select 成功 | `CONNECTED` | 由 communicatable 监听器驱动 |
| `CONNECTING` | 失败 / T3 超时 | `FAILED` | `auto_reconnect=0` 时立即 `comm.close()` |
| `CONNECTED` | `disconnect()` / 对端断开 | `DISCONNECTED` | 保留目标与采集设置 |
| `FAILED` | `connect()` | `CONNECTING` | 使用者点击，或 `auto_reconnect=1` 的退避定时器 |
| `FAILED` | `disconnect()` | `DISCONNECTED` | 清掉错误，回到可编辑的断开态 |

`FAILED` 是**终态**：没有自动离开它的边，只有使用者显式 `connect()`、或 `auto_reconnect=1` 的退避定时器才会再走 `CONNECTING`。主机没有 `LISTENING` / `STOPPED`——它永远是 ACTIVE 侧，进程启动后一律先落 `DISCONNECTED`。

五条硬约束（追加需求 6 / 7）：

1. **无绑定**：`host` 表不存 `sessionId` / `deviceId`，`HostSimulator` 不持有设备会话引用，也不从设备取 `ResolvedEquipment`；`127.0.0.1:5000` 与其他地址一样只是一个普通目标。
2. **无级联**：设备 `disconnect() / reload() / delete()` 都不调用主机注册表；主机 `connect() / disconnect() / destroy()` 也不查询设备是否存在。设备关闭只影响 `device_link`，主机断开只影响该实例的 `host_link`。
3. **无数量限制**：实例按 `hostId` 全局唯一寻址，删除「一台设备只允许一个本机主机」检查；N 台主机可并存、可指向同一地址。协议层已核实：设备侧对第二条 Select.req 回 `ALREADY_USED(3)`（`AbstractHsmsSsPassiveCommunicator.java:343-358`），且按引用比较保住已 SELECTED 的链路（`AbstractHsmsSsCommunicator.removeSelectedConnection`，`:128` 起，javadoc 明确「必须比对引用」），**在位主机不会被后来者踢掉**；后来者单独记 `FAILED`。
4. **配置自带**：每台主机自带目标地址、超时、采集 SVID 列表与声明类型、变量目录、自动重连开关；断开后这些设置全部保留，重连后恢复采集。
5. **失败必须真的停下**：`secs-protocol` 冻结不可改，而 ACTIVE 侧内部是 `for(;;)` + T5 无限重连（`AbstractHsmsSsActiveCommunicator.java:42-47,198-208`）。若只是把相位标成 `FAILED` 而留着 communicator，它会每 ~20s 静默重试，并在在位主机断开的一瞬间抢到链路——「互不影响」就被破坏了。因此 `auto_reconnect=0` 时失败即 `comm.close()` 销毁 communicator，重试完全由主机侧自己的退避定时器负责。

#### 2.4.2 接口与实现改造

`SessionRuntime`（`secs-app`）**现有方法一律保留**（`SessionRuntime.java:13-432`，共 40 个方法声明、38 个方法名——`previewJson` 有 3 个重载；含 `state / lastError / deviceName / configName / unitCount / hasPeer / counters / controlState / eventsJson / overviewJson / overviewJson(boolean) / setEventEnabled / add|update|removeEventPlan / add|update|removeReport / add|update|removeCeid / add|update|removeSvid / pin|unpinSvidValue / previewJson×3 / previewBinary / emitCeid / emitAlarm / sendSml / hostTarget / alarmsJson / terminalMessagesJson / catalogJson`）。本次只新增链路粒度，**不得按「只有 id/open/close」去重写接口**：

```java
public interface SessionRuntime {          // 现状不 extends AutoCloseable，不要顺手改继承关系
    // …上述现有方法一律不动…

    void disconnect();                     // 需求 1：只断链，对象与状态保留
    void reconnect() throws IOException;   // 复用同一对象重开端口/连接
    LinkPhase linkPhase();                 // 链路相位，与 state() 的会话状态并存
    // close() 语义收窄为「销毁」：disconnect + 释放全部引用，仅 delete 调用
}
```

两个现有方法带设备→主机的反向耦合，随需求 6 一起处理：

- `overviewJson(boolean hostSim)`（`:132`）的「本机主机模拟器是否占用」参数**删除**，设备 overview 不再含主机占用标记；只保留无参版本。
- `hostTarget()`（`:394`）与 `catalogJson()`（`:429`）**保留但主机域不再调用**：前者只供 v1 兼容层在创建瞬间解析目标地址（§2.5），后者只供设备页自己的结构化 UI。主机侧的变量目录改走 §2.4.2 的 S1F11 机制。

`HsmsSessionRuntime` 落地要点：

- 抽出 `LinkHandle`（communicator + 三个 ACK 线程池 + dispatcher + ticker），`disconnect()` = `LinkHandle.stop()`：`eventTicker.stop()` → `scheduler.pause()` → `tracePump.reset()` → `comm.close()` → `comm=null` → `communicatorState=NOT_SELECTED`、`controlState=OFFLINE` → 发布 `device-link` SSE。**不清** `model / values / effects / pinned / scheduler.disabledPlans / hostReports`。
- `reconnect()` = `HsmsConnector.open(currentSpec)` 重新填 `LinkHandle`（`open()` 现有逻辑本来就支持重建线程池与 dispatcher，`HsmsSessionRuntime.java:771-848`），`scheduler.resume(now)` 把 `lastFireMs` 锚到当前时刻，**不补发断开期间的周期事件**（沿用 ADR 0005，避免重连瞬间报文风暴）；从 `runtime.db` 重新灌入 pin 与 plan 启用态。
- `SessionManager` 的 `remove(id)` 改名为 `destroy(id)`，只由显式删除调用；`closeAll()` 停机时改为对全部实体 `disconnect()`（进程退出即可，DB 里的 `device_link` 在下次启动对账时统一置 `STOPPED`）。
- `SessionLauncher.close(id)` → `disconnect(id)`：不再删除 `sources`，把 `sessionId → config 文档 revision + overrides + lastGood` 记到 `runtime.db`；`destroy(id)` 才删。
- `RuntimeApi.closeSession(id)` **删除** `hosts.closeAllOf(sessionId)` 调用：设备断开不再触碰主机注册表；主机实例保持原状态，若要断开由使用者在主机侧单独操作。
- 端口：`requirePortFree()` 排除自身即可；重连前再查一次，被别的设备占用则回 `409 port-in-use` 并保持 `DISCONNECTED`。

`HostSimulator` / `HostSimRegistry` **领域解耦清单**（追加需求 6 / 7）：

- 创建入口从 `open(String sessionId, String targetJson, String hostId)` 改为 `open(HostCreateRequest)`：`{name, targetHost, targetPort, targetDeviceIdNum, timeouts?, collector?, autoReconnect?}`（`targetDeviceIdNum` 是 SECS 报文头的 Device ID 号，**不是设备实体 id**）；**删掉 `sessions.find(sessionId)` 存在性校验**。
- 删除 `HostSimulator` 的 `sessionId` 字段与 `localModelOf(runtime)` 派生；`stateJson()` 去掉 `session` / `mode` / `remote` 三类归属字段，只保留 `id / name / target / phase / lastError`。
- 删除 `hostsBySession` 索引、`hostIdOf()` 与全部 `xxxBySession` / `closeAllOf()` 方法；`RuntimeContext` / `ApiContext` 的 `openHostSim(sessionId, …)` 系列重载收敛为 `openHost(HostCreateRequest)` / `closeHost(hostId)`；`SessionHandler.java:466-502` 的 `POST /sessions/{id}/host-sim` 废弃。
- 本机模式与远程模式合并为「目标地址」一种概念：`connect()` 直接用 `host.target_*` 构造 `HsmsSsCommunicatorConfig`（ACTIVE、`isEquip=false`），不再区分 `override != null`，也不再挂 `installPassThrough` 的设备侧分支。
- 采集器不再依赖设备的 SVID 目录：SVID 列表、采样周期、解码类型由 `host.collector_json` + `host.variable_catalog_json` 自带。**解码改动很小**：现有 `decodeS1f4 → decodeScalar`（`HostSimulator.java:543-601`）本来就是格式码探测（`getDouble→getInt→getByte→getBoolean`），不读设备模型；只需把「未声明类型」的兜底提示记到该实例的收发记录里一次。
- **`localModel` 的实际用途只有 4 处**（SVID 存在性校验 `:431-437`、`staleSvids` `:662-668`、`mode` 标签 `:673`、`isRemote()` `:798`），删除成本远低于预期；S1F3/S1F4、S6F1 Trace、自动 ACK、CEID 启停全部与模型无关。
- **「变量自动获取」必须换实现路径**（否则 §3.4.2 的承诺无法兑现）：现状是前端 HTTP 读**设备页当前选中会话**的目录（`HostSimCollectPanel.tsx:72` 与 `HostSimFdcPanel.tsx:82` 消费的 `backend.catalog` 由 `useBackend.ts:254` 调 `client.catalog(activeSession)` 预加载，来自 `SessionRuntime.catalogJson()`），既依赖设备、又绑错了对象。解耦后改为**向本实例的目标发 SECS 查询**：
  1. `POST /hosts/{id}/variables/refresh` → 发 `S1F11 W <L>`（空列表 = 枚举全部），解析 `S1F12` 的 `SVID / SVNAME / UNITS`，写入 `host.variable_catalog_json`；设备侧已支持该语义（`HostCommandHandler.java:729-756`）。
  2. **`S1F12` 不含类型字段**，所以解码类型永远无法自动获得：`declaredType` 只能由使用者声明，未声明时走格式码探测兜底。界面必须把「名称/单位可自动读取」与「类型需声明」分开表达。
  3. 第三方对端可能不支持 S1F11：超时或回 `S1F0`/abort 时保留已有目录、提示「目标未提供变量清单，请手动填写」，并把该实例切到「变量需手动填写」形态，不报错、不影响连接。
- **链路相位必须有事件源**：现有 `HostSimulator.doOpen()`（`:205-206`）只注册 receive 与 pass-through，**不注册 communicatable 监听器**，掉线只在发送失败时才发现（`:719-723`）。必须补 `addSecsCommunicatableStateChangeListener`，由它驱动 `host_link.phase` 与 `host-link` SSE；否则徽标会长期停在错误的相位。
- **`FAILED` 终态与重试归属**：`auto_reconnect=0` 时，连接失败或收到不可通信事件即 `comm.close()` 销毁 communicator（不能留着让 ACTIVE 侧内部 `for(;;)`+T5 循环自己重试，见 §2.4.1 约束 5），相位置 `FAILED`、写 `last_error`、`next_retry_at=NULL`；`auto_reconnect=1` 时由主机侧退避定时器（建议 5s 起、指数退避、上限 60s）重建 communicator，并更新 `retry_count / next_retry_at`。
- **每主机报文归属（解决串台与重复计数）**：
  - `installPassThrough()` 去掉 `!isRemote()` 门槛，**所有主机都发布主机侧报文**，`MessageEvent.ofHost(hostId, …)` 不再带 `sessionId`；
  - 但这会与设备侧已发布的报文**重复计数**（进程内目标时同一帧被记两次）。因此 `MessageEvent` 增加 `perspective`（`device` | `host`），`MessageLog` 落盘与 SSE 都带上；设备页只读 `perspective=device`，主机页只读 `perspective=host`，**不做跨域去重、不查对方是谁**；
  - `MessageLog.select()`（`:504-533`）增加 `hostId` 与 `perspective` 过滤参数，`GET /hosts/{id}/messages` 才能真正做到按实例隔离；
  - 前端 `shared/lib/hostMessages.ts` 的 `localHostBySession`（`Map<session, 单个 hostId>`）**整段删除**，改为直接按 `hostId` 归属——这是需求 7 多开的前提。
- **主机 id 持久化**：`HostSimRegistry.java:63-65` 的 `"host-" + hostSeq.incrementAndGet()` 改为从 `config.db.host` 取持久 `host_01J...`；重启后 id 不变，v1 别名与前端深链才稳定。
- 删除 `HostSimRegistry.java:91-104` 的唯一性检查与前端 `HostTargetPicker.tsx:31-34` 的置灰逻辑；全局实例数不设上限。
- 把私有 `connect()` 提为 `public connect()`；新增 `public disconnect()` = 停采集器 + `comm.close()` + `open=false` + **保留实例、目标与采集设置**；`reconnect()` = `disconnect(); connect();`。`collector_json` 里带一个 `enabled` 位（采集启停）：断开保留，`connect()` 成功后 `enabled=1` 的实例自动恢复采集（兑现「重连后恢复采集」），`enabled=0` 的不自动启动；进程重启后主机一律 `DISCONNECTED`，采集只随显式 `connect()` 恢复。
- `HostSimRegistry.closeById()` → `disconnectById()`（**不 `hostSims.remove`**）；新增 `destroyById()` 才删实例。
- `stateJson()` 断开返回 `open:false, phase:"DISCONNECTED"`；`jsonById()` 对「存在但已断开」返回 200，前端不再把 404 当作断开。

#### 2.4.3 SSE 生命周期事件

在现有帧（`s6f11 / alarm / session / message / heartbeat`）之外增加四类，**现有帧一律不动**：

| type | 载荷 | 发布点 |
|---|---|---|
| `device-link` | `{deviceId, phase, controlState, port, at, reason}` | `connect / disconnect / reconnect / 对端断开 / 失败` |
| `host-link` | `{hostId, phase, target, at, reason}` | `HostSimulator.connect / disconnect` |
| `config-changed` | `{deviceId, revision, actor, at}` | `saveDocument / updateConstants / 回滚` |
| `plan-fired` | `{deviceId, executionId, planId, ceid, status, messages, effects, at}` | `PlanExecutor.commit()` |

前端据此实时刷新链路徽标与执行时间轴，不再靠轮询「发现对象不见了」。`host-link` 只驱动主机列表的那一行、侧栏实例点与当前打开的主机详情头，不触发设备页刷新；`device-link` 也不触发主机页刷新。

**`plan-fired` 必须节流**：计划周期最小可配到 1ms、`events.maxPerSec` 默认 50 且无上限，逐条推送会把 SSE 与前端时间轴打爆。规则：同一设备 200ms 窗口内的 `plan-fired` 合并为一帧（携带该窗口的执行摘要数组），明细仍逐条落台账、由 `GET /runtime/executions` 按需拉取；`status=FAILED` 的记录不合并、立即推送。

#### 2.4.4 启动对账

**两条规则各自独立执行，互不查询对方**：

- 设备侧：`device` 表里 `auto_start=1` 且未软删的设备 → 按 `connection_spec` 建 `SessionRuntime` 并 `connect()`，成功后从 `runtime.db` 灌回钉值、计划启用态、运行时计划正文、运行时目录编辑、主机动态报告（§2.4.1 的五张表）；没有 `device_link` 行的在册设备视为 `STOPPED`（不建行也不补行）；runtime.db 里 `device_id` 不在「未软删设备集」内的残留行——链路、五张运行态表、执行台账、`link_event`——统一删除（删除事务只清 config.db，这一步补上 runtime 侧的清理）。
- 主机侧：`host` 表里未软删的实例一律先置 `DISCONNECTED`；只有 `auto_reconnect=1` 的才各自按 `target_*` 尝试连接，失败留 `FAILED` 终态、写 `last_error`、`next_retry_at=NULL`，**不自动重试**；`auto_reconnect=0` 的启动后不连接。`host_link` 里指向已软删主机的残留行 → 删除。**不检查目标设备是否存在、是否在线、是否属于本进程**。
- 顺带执行保留策略裁剪：`config_revision` 每设备留最近 200 版、`plan_execution` 每设备留最近 5000 条或 7 天；此后每小时增量清理一次。

**不做跨库事务、不做跨实体一致性检查**，靠这份确定性规则收敛。

**v1 兼容（过渡期一个版本）**：

- **id 解析规则（前提）**：v1 路径里的 `{id}` 一律先按 `device.legacy_id` 解析（现状 `sessionId` 就是配置文件名 stem，见 §0.6），解析不到再按 `device.id` 试。v1 响应里的 `id` / `session` 字段继续回 `legacy_id`，旧前端深链 `#/device/{id}`、CLI 脚本、`--config` 才不会断；迁移后新建的设备没有 `legacy_id`，用 `device.id` 充当 v1 id。
- `DELETE /api/v1/sessions/{id}` → 内部转 `link/disconnect`，响应附加头 `Deprecation: true` 与 `Sunset`，并在 body 里带 `hint:"use POST /api/v2/devices/{id}/link/disconnect"`；
- `DELETE /api/v1/host-sims/{id}` → 内部转 `hosts/{hostId}/disconnect`；
- `POST /api/v1/host-sims` → 请求体里的 `session` **只在创建时一次性解析成目标地址**（按 `legacy_id` 找到设备，读 `SessionRuntime.hostTarget()` 的 `bindHost/port/deviceId` 填入 `target_*`），**不写入 `host` 表、不建立长期引用**；给了 `host/port` 则直接用它；此后该主机与那台设备再无关系；
- `POST /api/v1/sessions/{id}/host-sim` → 废弃，返回 `410 Gone` 并提示改用 `POST /api/v2/hosts`；
- `GET /api/v1/host-sims` → 返回全部主机实例，不再按 `session` 过滤；`session` 字段为兼容保留但恒为空串，`mode` / `remote` 同样保留为兼容字段（`mode` 恒为 `"target"`、`remote` 恒为 `true`），避免旧前端因字段缺失而崩；
- `GET /api/v1/sessions` → 由 `device` + `device_link` 组装（**已断开的设备仍在列表里，只是 `state=DISCONNECTED`**），保证旧前端不把设备「看丢」；
- `GET /api/v1/configs` / `PUT /api/v1/configs/{name}` → 映射到 `config_document`，`name` 视作 `device.name`。`If-Match: <ms>` 由 `config_document.updated_at`（毫秒）承担，服务端换算成 revision 比较；新写入一律用 `If-Revision`；
- `POST /api/v1/sessions` → 若设备已存在则视为 `link/connect`，否则先建实体再连接。

`docs/openapi.yaml` 增加 v2 全部 path，同一个 path 多方法合并声明（沿用现有契约检查脚本）。

### 2.6 配置态 / 运行态分层（需求 4 的后端支撑）

| 维度 | 配置态 | 运行态 |
|---|---|---|
| 库 | `config.db` | `runtime.db` |
| 命名空间 | `/devices/{id}/config/**`、`/templates/**` | `/devices/{id}/link/**`、`/devices/{id}/runtime/**` |
| 写者 | 界面保存、结构化编辑、S2F15 ECV、模板管理、迁移 | 设备心跳、PlanExecutor、S2F33/35/37 |
| 生效时机 | 使用者编辑：保存后成为**新版本**，需 `link/reload` 才进入运行。S2F15 回写：同事务追平运行版本，立即生效、**不产生漂移**（§2.3.2） | 立即生效，`reload` 会清空 |
| 失败语义 | 校验不过则整份不动（事务回滚） | 单次执行失败记台账，不影响设备 |
| 审计 | `config-changed` + `config_revision` | `plan-fired` + `link_event` + 现有 `audit.jsonl` |

**主机不属于这张表的任何一列**：`/hosts/**` 是第三个独立命名空间，主机自己的目标、超时、采集设置存 `config.db.host`，运行相位存 `runtime.db.host_link`，既不写设备的 `config_document`，也不进设备的三张运行态编辑表。

**配置漂移可见**：`device_link.config_revision` 与 `config_document.revision` 不等时，`GET /devices/{id}` 返回 `drift:true` 与 `pendingChanges:[...]`，前端显示「配置已改，尚未重载」横幅。**漂移只由使用者编辑产生**：S2F15 的设备常量回写在同一事务里追平 `device_link.config_revision`，因此主机写常量不会挂横幅、也不会诱使使用者去做会清空运行态编辑的「重载」。

**主机侧的对应物（需求 9 同构）**：主机没有设备正文，因此不做「正文重载」判断；但界面要与设备一样有「设置待生效」横幅，改为比较 `host.setting_revision` 与 `host_link.applied_revision`——保存目标、超时或采集设置只让前者 +1，`connect` / `apply` / 下发采集配置成功后才追平后者。两侧横幅位置、配色、按钮数一致，语义各自独立，互不读写对方的字段。

### 2.7 事件编排执行器（需求 5）

#### 2.7.1 数据模型扩展

`EventPlan`（`secs-core`）从

```java
record EventPlan(String id, int ceid, Trigger trigger, List<EventEffect> effects)
```

扩为

```java
record EventPlan(
    String id, int ceid, Trigger trigger,
    List<EventEffect> effects,       // SVID 变化
    List<PlanAction> actions,        // 要发的消息（为空时向后兼容 = 一条 S6F11）
    OfflinePolicy offlinePolicy,     // skip | queue | fail
    FailurePolicy onSendFailure      // keep | rollback
)
```

`PlanAction`（`secs-core/event`，纯数据、不含 I/O）：

```java
record PlanAction(Kind kind, Integer stream, Integer function, boolean wbit,
                  String sml, Map<String,String> params) {
    enum Kind { S6F11, SML, ALARM, TERMINAL, TRACE }
}
```

- `S6F11`：按 CEID 走现有 `S6F11Assembler`（配置里省略 actions 时的默认值，保证 v4/v5/v6 配置零改动）；
- 配置正文与运行库 `plan_action.kind` 使用同一组取值：`s6f11 | sml | alarm | terminal | trace`（界面展示名分别为 事件报告 / 自定义 SML / 报警 / 终端消息 / Trace），原型里的示例 JSON 亦按此拼写；
- `SML`：走 `SmlParser` + `SmlSender` 的受控子集，报文体支持 `{{svid.1001}}` 这类**运行时占位符**，在发送前用同一个 `ValueSourceHandle` 求值；
- `ALARM` / `TERMINAL` / `TRACE`：复用 `AlarmReporter` / S10F1 / S6F1 组装；
- 编译期新增校验：`UNKNOWN_ACTION_SVID`、`BAD_SML_TEMPLATE`、`EFFECT_TYPE_MISMATCH` 扩展到运行时编辑路径（修 G4）。

`Fire` 仍保持 `(atMs, planId, ceid)` 的语义以维持 ADR 0005 的纯区间查询；**新增可选的第四分量 `snapshot`**，在调度器产出 Fire 时挂上当时 `plan.actions/effects` 的不可变引用，修 G6：执行时优先用快照，快照缺失再回查实时表。落地约束：

- 保留三参兼容构造器（`EventSchedule.between():69` 现在用 `new Fire(atMs, planId, ceid)`），第四分量缺省为 `null`；
- **挂共享引用，不做深拷贝**：`EventPlan.effects` 已是 `List.copyOf`，每个 Fire 只多一个指针；深拷贝会按效果条数放大内存；
- **预览路径不挂快照**：`EventSimulator` 单次可产出上千个 Fire（`DEFAULT_MAX_EVENTS=1000`、`MAX_TICKS=1_000_000`），预览只需要事件标记；
- `Fire` 从不进 JSON（API/预览输出走 `EventSimulator.SimFire`），也没有 `Set`/`Map` 依赖其 `equals`，因此加分量不破坏任何对外契约。

#### 2.7.2 `PlanExecutor`：一次触发 = 一条台账

`secs-runtime/session/PlanExecutor.java` 接替 `EventReporter.emit()` 成为唯一执行入口：

```
firePlan(planId, ceid, atMs)  [EventScheduler 统一过滤：enabled / S2F37 / RateLimiter]
  │
  ├─ 1. reserve：内存幂等表判重（deviceId|planId|atMs[|step|seq]）→ 占位，重复触发直接跳过
  ├─ 2. canSend?  ONLINE + communicatable
  │       ├─ 否 → offlinePolicy=skip  → status=SKIPPED, skipped_count++, 不发不改（ADR 0005）
  │       │        offlinePolicy=queue → 入有界队列(≤256)，重连后按 FIFO 补跑（不是 Spooling，不落 S2F43）
  │       │        offlinePolicy=fail  → status=FAILED, error='host-offline'
  ├─ 3. applyEffects：EventEffectStore.apply(...)，逐条记 before/after
  │       （顺序：先效果）
  ├─ 4. buildMessages：按 actions 顺序构造；S6F11 / SML 占位符都从同一个
  │       ValueSourceHandle 取值 → 读到的是"变化后的值"（保持 2.0.1 先 apply 后 build 语义）
  ├─ 5. send：逐条 comm.send，记 stream/function/wbit/sml/sentAt/elapsedMs/ack
  ├─ 6. 结果：全部成功 SENT / 部分 PARTIAL / 全失败 FAILED
  │       onSendFailure=rollback 且全失败且效果全为 set/add → 回滚（记 rollback 到台账）
  └─ 7. commit：台账行入异步写队列 → 批量落库 + SSE plan-fired（节流）+ 审计
              + runtime_plan_state 计数内存累加、随批量落库
```

要点：

- **顺序契约写进测试**：`effects` 一定在 `build` 之前，`build` 一定在 `send` 之前。这样「启用之后按计划发送消息，且执行 SVID 的变化」不是两个偶发副作用，而是一次可观测的执行。
- **台账绝不在发送线程上同步写盘**：现状 `emit` 同步跑在 100ms ticker 线程上（`EventTicker.java:18` → `EventScheduler.pumpEvents` → `firePlan` → `emit`），默认 50 次/秒/设备、`events.maxPerSec` 无上限、`Trigger.Periodic` 最小 1ms。若每次 fire 都同步 `INSERT`+`UPDATE` 并抢全库单写者锁，磁盘延迟会直接拖慢**所有设备**的报文发送。因此 reserve 用内存幂等表，台账走专用异步批量写队列（每 50ms 或每 64 条 flush），发送线程只做内存操作。进程崩溃最多丢最后一个 flush 窗口的台账，不影响已发出的报文与已施加的效果。
- **幂等键** `deviceId|planId|atMs`：心跳重复扫描、服务重启后补算都不会重复改值/重复发报；单步试跑追加 `|step|<seq>` 以免与真实触发撞键；**预览（`EventSimulator` / `config-preview`）一律不写台账**。
- **值一致性**：S1F3/S1F4、S6F11、S6F1/Trace、预览仍然共用 `EffectValueSource`（`HsmsSessionRuntime.java:268-272` 的装配保持），只是现在有台账能证明变化发生过。
- **`rollback` 的适用边界（不能按字面实现）**：`EventEffectStore` 只有 `apply/activeAt/hasActive/clear`，**没有移除或逆操作**；`RESUME` 的语义是清空该 SVID 整个队列（会波及别的计划、别的触发），`pulse/shift` 是时间态且 decay 基线依赖前序效果，每 SVID 64 条 FIFO 还可能已把本次条目挤出。因此：
  - 只对「本次全部效果都是 `set/add`」的计划开放 `rollback`；含 `shift/pulse/resume` 的计划在编译期与运行时编辑路径都**拒绝**该组合（`EFFECT_ROLLBACK_UNSUPPORTED`）；
  - 新增 `EventEffectStore.remove(handle)` 按条目句柄摘除，且**仅当此后没有其它 fire 触碰过这些 SVID** 才执行；否则台账记 `rollback_skipped` 并保持效果；
  - 钉值优先于效果（`EffectValueSource:84-87`），rollback 不动钉值。
- **`queue` 补跑的时间锚点**：消息按原 `atMs` 记入台账以便追溯，但**效果一律按补跑时刻 `now` 重新施加**——pulse/decay 是时间函数，用原 `atMs` 会让曲线错乱。队列是内存态、进程重启即丢，界面与文档都标注「不是 Spooling，不实现 S2F43–F48」。
- **失败策略显式化**：默认 `keep`（保持 2.0.1 行为），可配 `rollback`（受上述边界约束）；写进 `config.db.event_plan`，前端可编辑。`PARTIAL` 一律不回滚。

#### 2.7.3 启用语义与调度状态

`POST /devices/{id}/runtime/plans/{planId}/enabled` 不再是纯内存 `disabledPlans`：

1. 写 `runtime.db.runtime_plan_state.enabled`；启用时 `start_at = now`、`next_fire_at = 下一次 fireTimes(now, now+period)`、`fire_count=0`（不清历史台账）；
2. `EventScheduler.setEventEnabled()` 同步内存集合（保留 ADR 0011 的禁用期清去抖/延迟队列、禁用期间不补发）；
3. 重连后由 §2.4.4 的对账从 `runtime.db` 恢复启用态、运行时计划正文（`runtime_plan_override`）与目录编辑（`runtime_catalog_edit`）；`link/reload` 时清空这两张 override 表并按 `config.db.event_plan.enabled_default` 重置（配置优先）；
4. `GET /devices/{id}/runtime/plans` 返回 `enabled / nextFireAt / lastFireAt / fireCount / skippedCount / lastError`，供前端倒计时与「启用后确实在跑」的证据。

`next_fire_at` 由 `Trigger.fireTimes(from, to, rng, planId)` 计算（纯函数、可回放，ADR 0005 不变），`OnCondition / AfterEvent` 没有确定下次时刻时返回 `null` 并显示「条件驱动」。

#### 2.7.4 配套修补

- **G2**：`POST /config-preview` 改用 `EventSimulator.simulateWithEffects()`，草稿预览与会话预览一致；前端「计划预览」在同一套结果上叠加。
- **G4**：运行时 `addEventPlan/updateEventPlan` 增加 `requireKnownSvid(svid)` + 类型检查，与 `SessionConfig.compile()` 共用判据。
- **G7**：离线策略可配，默认 `skip`（不补发、不缓存），`queue` 是**有界内存队列**且明确标注「不是 Spooling，不实现 S2F43–F48」，避免现场误解。
- **预览边界**写进 UI：预览是「配置的确定性影子」，钉值、手动触发、64 条 FIFO 挤出不可重放（沿用 `svid-value-model.md:322-329`）。

## 3. 前端设计

### 3.1 信息架构（两段式）

**侧栏三组（第三轮修订 11，覆盖原型初稿的四组形态）**：

```
设备清单   工作台(设备列表入口) + 动态设备树(状态点)
主机清单   主机模拟(列表页入口) + 动态主机实例树(同一套状态点)
独立工具   主机模板 / 设备模板 / 审计
```

```
工作台  ── 设备列表（含"已断开"），批量 连接/断开/重载，删除只在此处二次确认
│         ※ 不展示主机实例
│
├─ 设备详情 #/device/{deviceId}/{zone}/{page}
│   ├─ 设备头：名称 · ID · 链路徽标 · 控制状态 · 配置版本 / 当前运行版本 · 端口
│   │           [连接] [断开] [重载] ⋯ [删除设备]
│   ├─「配置待生效」横幅：配置已更新到 v7，当前运行仍是 v6 → [重载使生效] [查看差异]
│   │
│   ├─【配置区 · 设备定义】蓝色系 + 文档图标 + "保存后需重载"
│   │   ├ 概览 / 连接 / 结构 / 值模板 / 事件计划 / 配置原文 / 设备常量 / 版本历史
│   │   └ 8 个子页都只描述「这个设备是什么」；「结构」含单元 / 状态变量 / 报告定义 / 事件定义与绑定
│   │
│   └─【运行区 · 当前运行】绿色系 + 实时脉冲 + "仅本次运行有效"
│       ├ 实时状态 / 事件执行 / 事件与报告 / 状态变量 / 报文收发 / 手动操作
│       └ 共 6 个子页；**没有「主机连接」子页**（追加需求 6）
│
└─ 主机模拟 #/hosts（与设备树平行的顶层入口，不是设备的子页）
    ├─ 主机列表：与「工作台」同构的 KPI + 表格，批量 连接/断开，删除在此二次确认
    │            ※ 新建只填目标地址，可连续新建任意多台
    │
    └─ 主机详情 #/hosts/{hostId}/{zone}/{page}（骨架与设备详情逐项对齐）
        ├─ 主机头：名称 · ID · 连接徽标 · 控制状态 · 设置版本 / 当前生效 · 目标地址 · 收发数
        │           [连接] [断开] [使设置生效] ⋯ [删除主机]
        ├─「设置待生效」横幅：设置已更新到 vN，当前生效仍是 vM → [使设置生效] [查看改动]
        │
        ├─【配置区 · 主机设置】蓝色系 + 与设备相同的图标与徽标
        │   ├ 概览 / 连接 / 报文模板 / Trace 设置 / 采集设置
        │   └ 5 个子页只描述「这台主机怎么连、发什么、采什么」
        │
        └─【运行区 · 当前连接】绿色系 + 实时脉冲 + "仅本次连接有效"
            ├ 实时状态 / 消息发送 / Trace 采集 / 数据采集 / 收发记录 / 手动操作
            └ 6 个子页承载现有主机模拟的全部操作
```

**同构的含义（追加需求 9）**：设备与主机共用同一套界面骨架——左侧各有一组实例树、顶部面包屑同为「域 / 实例 / 分区」、实例头同为「名称 + 两枚徽标 + 四项指标 + 三个按钮」、下面同为「配置区 / 运行区」两段式页签、保存后同样出现待生效横幅。两个域只是长得一样，**数据、接口、生命周期仍然完全独立**：主机页不读设备列表，设备页不读主机列表，任一侧连接或断开都不刷新另一侧。

主机模拟页按追加需求 6 / 7 保持**独立多开**：

- 新建主机只填「名称 + 目标地址 + 端口 + Device ID」，**没有设备下拉框**；目标可以是任意设备或第三方模拟器的地址；可连续新建任意多台，多台可指向同一地址。
- 每台主机独立连接 / 断开 / 删除；断开的行仍留在列表里显示「已断开」，可一键重连；删除移到 `⋯` 并二次确认。
- 状态四态：`已连接 / 连接中 / 已断开 / 连接失败`；「连接失败」是终态，不显示「重试中」，除非使用者打开了「自动重连」。任一台状态变化不影响其他主机，也不影响任何设备。
- 原有控制台能力不删：发 SML、常用命令、收发记录、采集启停，按「设置 / 操作」分别落到配置区与运行区（见 §3.4）。
- 设备详情页与工作台**不再出现主机实例列表或主机连接状态**；设备报文页只显示报文内容与来源地址。

### 3.2 关键交互

1. **断开 ≠ 删除**：设备头「断开」是普通按钮（非 danger），不断开页面、不弹「确定删除」；按钮点击后徽标变灰「已断开」，配置区仍可编辑，运行区显示空态「链路已断开，重新连接后恢复」。工作台该设备行保留，操作列变「连接」。
2. **删除是显式危险动作**：`⋯ → 删除设备`，弹窗要求输入设备名，列出会删除的内容（配置正文 + 全部版本 + 运行态编辑 + 执行台账），且链路未断开时禁用并提示先断开。
3. **配置区 / 运行区的边界**：配置区每个面板右上角固定一枚「版本 vN · 已保存」徽标与「保存后需重载」提示；运行区固定一枚「当前运行 · 仅本次有效」徽标。两区使用不同的强调色与图标，页签组之间有分隔线与小标题，避免误认。界面不出现存储、接口、模块等实现词（见 §3.5）。
4. **配置待生效**：保存配置后立刻出现横幅「配置已更新到 v7，当前运行仍是 v6」；「重载使生效」一键调用 `link/reload`，成功后横幅消失、运行版本追上配置版本。
5. **事件执行页**（需求 5 的可视化落点）：
   - 顶部：计划卡片列表，每张「启用」开关 + 下次触发倒计时 + 累计触发/跳过数 + 最后错误；
   - 中部：**时间轴**，每条执行记录显示 `时刻 · 计划 · CEID · 状态(SENT/PARTIAL/FAILED/SKIPPED) · 报文条数 · SVID 变化数`，点击展开明细（发过的 SML 原文 + 每个 SVID 的 before → after）；
   - 下部：SVID 曲线叠加事件竖线，跳变与台账里的 `after` 对齐；
   - 工具条：单步试跑 / 暂停全部 / 只看失败 / **含试跑** / 导出 CSV。试跑记录带「试跑」标记、默认隐藏、**不计入累计触发数**，也不推进下次触发倒计时。
6. **状态实时化**：SSE `device-link / host-link / config-changed / plan-fired` 分别驱动设备徽标、主机列表行与详情头、待生效横幅、执行时间轴，不再依赖 2 秒轮询发现「对象消失」；其中 `host-link` 只刷新对应那台主机。
7. **主机与设备同构的导航**（追加需求 9）：左侧「主机模拟」进入与工作台同构的列表页 → 点「详情」或侧栏实例进入主机详情；侧栏实例树、面包屑、实例头、两段式页签、「设置待生效」横幅与设备逐项对齐。切换分区只换子页内容，页面骨架不变。
8. **主机多开与功能保留**（追加需求 7 / 10）：「新建主机」不弹设备选择器，直接展开目标地址表单；创建后新行追加到列表、计数 +1、侧栏多一项；可对两台主机分别连接 / 断开，互不影响。每台主机的详情页既能改设置，也能发报文、配 Trace、跑采集、看监控，操作方式与设备运行区一致。
9. **设备侧功能同样一项不删**：现有 10 个子页按 §3.3.1 的归位表落到新 14 页。其中「事件与报告」运行页承接 `CeidPanel` 的 events / reports 双模式（本次运行临时增删改 CEID / 报告 + 手动触发），「手动操作」承接 `AlarmsPanel` 的报警置位 / 清除（ALID + 文本 + 类别）与 `SendPanel` 的 SML 发送与压测。**配置里没有报警定义**，所以报警只出现在运行区，不新增配置页。
10. **主机连接失败是终态**：列表与详情头显示红色「连接失败」+ 最后错误，**不显示「重试中」**；只有使用者点「连接」或打开了「自动重连」才会再试。多台主机指向同一地址时，先连上的保持「已连接」，后来者显示「连接失败 · 目标已有主机」，两者互不影响。
11. **变量自动获取与类型声明分开**：主机配置区「采集设置 / Trace 设置」提供「从目标读取变量」按钮，成功后填充 SVID 的名称与单位；**解码类型仍需使用者声明**（目标回复里没有类型信息），未声明时按数值兜底并在该实例收发记录里提示一次。目标不支持该查询时提示「目标未提供变量清单，请手动填写」，并切到手动填写形态，不影响连接。

| 钉值 / pin | 手动设定 |
| 运行态 · 不写盘 | 当前运行 · 仅本次有效 |
| `SSE device-link` | 实时更新 |
| `BEGIN IMMEDIATE / reproject / If-Revision` 流程卡 | 整段删除 |
| 设计与后端映射 / 双库架构图（仅存在于原型） | 整个视图删除 |

同时删除与操作无关的说明页、架构图、实现映射表、迁移来源与回滚参数等技术段落；「保存语义」「保存管线」「连接与实体的关系」「S2F15 写入路径」「回滚规则」「值优先级」「幂等键」「链路事件流的接口名」等解释性卡片全部移除，只保留可操作的控件与结果列表。这些技术信息保留在本文与 ADR 0017 中。

**检查脚本的判定规则**（`scripts/check-ui-words.ps1`，进 `check-all.ps1`）：

- 扫描范围：`frontend/src/**/*.tsx|ts` 的**字符串字面量与 JSX 文本**，不含注释、类型名、变量名、`import` 路径。注释里写 `plan_execution` 是允许的。
- 「表」必须按词判定，不能裸匹配单字：命中 `数据表 / 建表 / 表结构 / 表名 / 单表`，放行 `列表 / 表格 / 报表 / 图表 / 仪表 / 表达 / 表示`。原型里「列表」出现 16 次、「表示」1 次，裸匹配会把它们全部误报。
- 英文技术词按词边界匹配（`SQLite`、`If-Revision`、`reproject`、`SHA256`），避免命中 `sqliteVersion` 之外的正常标识符；`SSE` 只查界面文案不查 `EventSource` 调用。
- 白名单集中放在脚本顶部一处，新增放行词必须写明理由；命中即 `exit 1` 并打印 `文件:行号:命中的词`。
- 同一脚本顺带检查 `docs/design/frontend-panel.html`，保证原型与产品文案同标准。

### 3.6 结构化编辑原型（secs-device-config-editor.html）的定位与映射

该原型是配置区「结构 / 配置原文」页的**交互探索稿**：树形导航 + L1–L5 层级徽章 + 逐字段表单 + SML 节点路径（`S6F11 W › L[3] › L[1] › …`）。评审结论：**交互骨架可沿用，数据层级不能照搬**——它建模的是另一套配置文档，与现有模型（schemaVersion=6）不一致：

| 原型节点（L1–L5） | 现有配置模型中的对应物 | 结论 |
|---|---|---|
| 设备（endpoint：transport/ip/port/sessionId） | `session`（`SessionSpec`：passive/bindHost/port/deviceId） | 对应「连接」页；原型多出 transport=SS/HSMS/DS 下拉，产品只支持 HSMS-SS，展示口径用 被动监听/主动连接 + Device ID（§3.4.1） |
| 文档（document 顶层） | `config_document.body` 原文 | 对应「配置原文」页 |
| 值格式（valueFormat.pattern/toInt） | **无对应键** | 超前设计；曲线/取值形状走「值模板」（templates.curves 等），不支持 pattern 重排 |
| 追踪（trace.enabled/dsperFormat/maxActiveTraces/queueCapacity/overflowPolicy） | 仅 `TraceLimits`（连接页的 Trace 上限）；DSPER 是 S2F23 报文内 A[6]，不是可配格式（`TraceSpec.java:31-32` 强制 ≥1 秒） | 超前设计；maxActiveTraces/queueCapacity/overflowPolicy/dsperFormat 不进首版 |
| 单元 → 基础与范围（unit/ceIdStart/ceIdEnd/interval/svIdStart/svIdEnd） | `UnitSpec`：`unitId / name / injectUnitId`（`SessionConfigJson.java:703`）；idSpace 区间在 `equipment.idSpace` | 部分对应「结构」页；**区间按 idSpace 全局分配，不是每单元起止号** |
| 单元 → SVID 明细 | `UnitSpec.svids` → `svid_def` 投影 | 对应「结构」页 |
| 单元 → 报告 / CEID（L4） | `UnitSpec.reports / UnitSpec.ceids` → `report_def` / `ceid_def` 投影 | 对应「结构」页报告定义 / 事件定义 |
| 单元 → 步骤联动（stepSvIds/stepChangeCeId）、SVID 规则模板（svIdTemplate/svIds）、启动自动配置（startAutoConfig）、自定义运行配置（customRunConfigs） | **无对应键** | 超前设计，不进首版 |
| 消息模板（messages，按 CEID 的 SML 变体） | **无对应键**（报文组装是 `EventReporter`/`PlanAction`，不是配置里的消息库） | 超前设计；「按计划发任意消息」由 §2.7.1 的 `plan_action` 承担，UI 归「事件计划」页 |
| 自动化消息（autoMessageConfig.automationMessageEntities）、消息描述集（messageDescSets）、报警自动配置（alarmAutoConfig） | **无对应键** | 超前设计；报警在产品里是纯运行态（§3.3.1），不新增配置页 |

落地规则：

1. **首版结构化编辑只覆盖既有键**：structured section 清单以 §2.5 为准（`connection / equipment / units / svids / reports / ceids / plans / templates / constants`），每段一个表单页，沿用原型的树形导航与层级徽章交互；
2. 原型中的超前分组（值格式 / 追踪策略 / 步骤联动 / SVID 规则模板 / 启动自动配置 / 自定义运行配置 / 消息模板 / 自动化消息 / 消息描述集 / 报警自动配置）在配置模型扩展之前**不进产品**；要落地必须先扩 schema（新 schemaVersion + 迁移 + §2.2.1 增补投影表 + 校验规则），按 ADR 流程另立决策；
3. 原型侧栏常驻芯片（`format / version / schemaVersion / exportedAt / device.revision`）违反 §3.5 的精神，产品里一律转成「版本 vN · 已保存」口径；
4. 原型顶部的注释块已标注同一结论，原型修订时与本文同步。

## 5. 风险与明确不做

| 风险 | 缓解 |
|---|---|
| JNI 破坏单文件原生镜像 | **M0 尖峰先验证**（现状：全仓无 GraalVM 反射/资源元数据，零 JNI 依赖，夜间只跑 Windows 且 `continue-on-error: true`）。过了才进 M1；连续失败则按 ADR 0017 兜底降级为「瘦 JRE + jar」，**方案 B 不是现成的**，打包脚本、安装器、发布说明都要改，需单独排期 |
| 正文与投影表双份数据漂移 | 投影表只由 `reproject(body)` 整体重建，禁止单表写入；启动时校验 `content_sha256`，不一致自动重投影 |
| 迁移误删用户 JSON | 导入全程复制语义，自检全部通过后才移动到 `legacy/`（失败则原地不动，work-dir 仍可用 2.x 启动，见 §2.3.3）；提供 `--export-config` 回滚；迁移前用 **`VACUUM INTO '<work-dir>/backup/config-<时间戳>.db'`** 做在线一致性备份（WAL 下直接复制 `config.db` 会丢掉未 checkpoint 的写入，不是有效备份） |
| S2F15 写常量产生永久「配置待生效」 | `updateConstants` 走独立写事务：升 revision 但**不写版本快照**，同事务把 `device_link.config_revision` 追平，因此不产生漂移；使用者手改配置才产生漂移（§2.3.2） |
| 「断开仍占端口」误解 | `disconnect()` 明确 `comm.close()` 解绑端口，UI 文案写「端口已释放，设备定义保留」 |
| 主机「连接失败」不是终态 | HSMS ACTIVE 侧是 `for(;;)` + T5 重连，不主动 `comm.close()` 就会永远重试。`connect()` 失败路径必须关链路，相位停在 `FAILED`，重连只由使用者点击或 `auto_reconnect=1` 触发（§2.4.1 约束 5） |
| 主机失去设备模型后变量无来源 | 改用 `S1F11` 空列表查询 + 每台主机自带目录；**类型永远无法自动获得**，需使用者声明，未声明按数值兜底并提示一次；目标不支持时切手动填写，不影响连接（§3.4.2） |
| `on_send_failure=rollback` 无法实现 | 只对 `set` / `add` 生效，且要求「此后没有别的 fire 触碰过该 SVID」，否则记 `rollback_skipped`；`pulse` / `shift` / `resume` 无逆操作（`EventEffectStore` 只有 64 条 FIFO，`RESUME` 会清掉别的 fire 的效果），一律不回滚；`PARTIAL` 不回滚；钉值不受影响（§2.7.2） |
| 高频编排把台账与 SSE 打爆 | 台账内存幂等预留 + 每 50ms / 64 行异步批量落盘；`plan-fired` 按 200ms 合并窗口推送，`FAILED` 立即推；台账保留 5000 行 / 7 天，版本快照保留 200 版 / 设备 |
| v1 客户端仍传 `session` 创建主机 | 兼容层只在创建瞬间把它解析成目标地址，不写入 `host` 表；旧端点 `/sessions/{id}/host-sim` 返回 410 并给出新路径；v1 的 `sessionId` 通过 `device.legacy_id` 解析 |
| 同一地址被多台主机连接 | HSMS 设备侧只接受一条 SELECTED 链路，多余实例置 `FAILED` 并各自记错；不再由注册表预禁，也不影响其他主机 |
| 主机 id 是进程内计数器，重启后失联 | `host.id` 改为持久 ULID，`runtime.db` 的 `host_link` / `runtime_host_report` 以它关联；重启后主机一律 `DISCONNECTED`，只有 `auto_reconnect=1` 才尝试 |
| 离线补发被当成 Spooling | `offlinePolicy=queue` 是有界内存队列，界面与文档显式标注「不是 S2F43–F48」 |
| 跨库一致性 | 不做跨库事务；用 §2.4.4 启动对账 + 幂等键收敛 |
| 在制改动与新设计冲突 | `localHostBySession`、监控页的 `logs/messages.jsonl` 文案、`installPassThrough` 门控必须在 M2 一并改，否则「主机多开互不影响」与需求 8 直接不成立（§0.6） |

**明确不做**：`secs-protocol` 任何改动；Spooling；鉴权体系；把报文/审计 JSONL 搬进 SQLite（保持 ADR 0009/0012）；把曲线改成有状态（ADR 0003）；把模板图改成带副作用（ADR 0004）。

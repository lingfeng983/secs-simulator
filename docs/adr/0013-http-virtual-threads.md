# ADR 0013 · HTTP 请求处理改用虚拟线程

- 状态：已接受
- 日期：2026-10-30
- 影响范围：`secs-api-http` 的 `HttpApiServer`（请求池、慢路由池、SSE 池），新增回归用例 `HalfSentBodyStarvationTest`

## 问题

JDK 自带 HttpServer 把每个请求交给执行器；处理器在等 `readBody`、等 T3 回复、
等 host-sim 建连时，会一直占着那根线程。固定 8 线程池时，十来条"声明了
`Content-Length` 却只发一个字节"的连接（或几条 W 位手动发送）就能让
health / 轮询 / 取票全部排队——界面上表现为"后端卡死"，但 CPU 和网络都是空闲的。

之前用"慢路由专用池 + 请求截止时间"缓解：慢请求分流到 4 个线程，
120 秒强制关闭交换。这是止血，不是治本：

- 慢路由清单是手写的，新路由忘了归类就回到老问题；
- 截止时间到了才回收，期间那 8 个槽位仍然被占着；
- 慢池本身只有 4 个槽，几个并发 T3 等待就开始 503。

## 决策

### 1. 请求池换成"每任务一个虚拟线程"

`Executors.newThreadPerTaskExecutor(Thread.ofVirtual()...)`。线程在等 socket 时
卸载载体线程，所以并发只受内存与 fd 上限约束，不再受"8 个槽"限制。

慢路由池保留，但语义从"避免线程饥饿"变成"**限制重活并发**"：编译草稿、
压测、host-sim 这类 CPU/内存型操作仍然最多 4 个并发、排队 16，超出回 503。
这个上限挡的是资源放大，不是线程饥饿，所以虚拟线程下继续有效。

SSE 池同样换成虚拟线程工厂，但保留"64 条上限 + 超出 503"的既有契约：
每条流大部分时间在等下一帧，用虚拟线程只是让它不再占平台线程。

### 2. 可回退

`-Dsecssim.http.virtual=false` 退回原来的固定线程池（8 个），用于排查
"是不是虚拟线程引起的"这类问题。回退模式是调试开关，不是等价替代：
`HalfSentBodyStarvationTest` 在回退模式下会超时失败，这是设计如此。

### 3. 不引入 Jetty

- 线程饥饿问题已经由虚拟线程解决，换服务器不再带来收益；
- Jetty 依赖树大，且 native-image 需要额外的反射/资源清单；
- 现有路由、审计、CORS、Host 校验都是围绕 `com.sun.net.httpserver` 写的，
  换服务器的风险远大于收益。

## 后果

- 半截正文、慢主机、W 位等待不再互相阻塞；关闭慢路由清单的维护负担仍在，
  但它现在只影响"重活并发上限"，不影响可用性。
- 协议层（HSMS/SECS-II）继续用平台线程：收发有明确的 T3/T6/T8 超时与
  专用队列，改虚拟线程没有收益，反而失去"线程数与连接数可预期"的排查便利。
- `-Pnative` 需要 GraalVM 25 对虚拟线程的支持；`NativeRuntimeIT` 覆盖了
  "原生镜像里 API + SSE + HSMS 全链路"，作为回归闸门。

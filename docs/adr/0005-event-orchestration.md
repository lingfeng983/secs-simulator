# ADR 0005 · 事件调度是纯函数，限流必须做在设备级

- 状态：已接受
- 日期：M4（S6F11 部分）
- 影响范围：`secs-core` 的 `event`、`secs-runtime` 的会话

## 问题

S6F11 什么时候发，看起来是个"定时器"问题，用 `ScheduledExecutorService` 直接排即可。
但在仿真器里有三个额外要求：

1. **可回放**：同一条编排，跑两次必须得到同样的时序（含抖动）。
2. **加速播放**：10 倍速时，事件时序也要同步压缩，不能靠真实定时器。
3. **可补算**：预览要能在 2 秒内算完 1 小时的编排结果，不能真的等 1 小时。

## 决策

### 1. 调度是"区间查询"而不是"定时器排队"

```java
List<Long> fireTimes(long fromMs, long toMs, Rng rng, String planId);
```

给定时间区间，直接算出该区间内的触发时刻。区间是**左开右闭**，
因此 `between(0,1000)`、`between(1000,2000)` 连续调用不重不漏。
抖动用 `rng.derive("plan:" + planId).uniform01(k)`，只依赖计划标识与序号，
所以可复现。

会话侧只是一层薄薄的心跳：每 100ms 调一次 `between(lastFire, now)`。

### 2. 限流必须是设备级的

多单元设备最典型的事故是"某个单元剧本配错，一秒发几百条 S6F11"，
主机侧的后果是 T3 排队、或直接判定设备异常。
因此 `RateLimiter` 挂在**会话（=设备）**上，而不是每个单元各管各的。

### 3. 没有主机在线时不积压

`communicatable` 为 false 时，心跳只更新 `lastFireMs`，不累计待发。
否则主机上线瞬间会涌出几百条历史事件——这在真实设备上不会发生，
也会让主机误判设备状态。

## 后果

- **正面**：编排可回放、可加速、可批算；限流在事故现场起作用。
- **负面**：区间查询天然不支持"依赖上一事件"的复杂触发（例如"A 事件后 2 秒再发 B"）。
  这类需求需要引入事件链（`AfterEvent`），届时把 `lastFireMs` 换成"已发生事件集合"即可，
  接口形状不变。
- **已实现（2026-10-18）**：条件触发（`OnCondition`，如"温度 > 190 才报"）。
  运行时每 tick 求值表达式，`ConditionDebouncer` 负责"连续成立 `debounceMs` 才触发一次"；
  主机掉线或事件被禁用时状态清零，重新上线需重新满足去抖时间。
- **已实现（2026-10-18）**：事件链（`AfterEvent`，A 之后 N 秒发 B）。
  源计划成功后把后继放入延迟队列，按计划时刻触发；配置层校验源计划存在且无环，
  运行时同 tick 最多级联 64 跳防失控。

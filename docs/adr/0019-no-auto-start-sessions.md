# ADR 0019 · 启动不自动开会话:设备存数据库,界面点击启动

- 日期:2026-11-14
- 状态:已接受
- 关联:[ADR 0017](0017-sqlite-config-store.md)(设备/配置入库)、[ADR 0018](0018-intranet-open-access.md)

## 背景

3.0 的 `--demo-session` 会把 classpath 里的两台演示设备**播种**进 config.db 并**立即启动会话**
(Bootstrap.startDemoSession);桌面壳也用它保证"打开即有设备"。实际使用中:

- 开机即监听 HSMS 不是期望行为——设备该不该跑、什么时候跑,应当由操作员在界面决定;
- 演示设备用 classpath JSON"设置默认设备"的方式与"设备存数据库"的模型相悖;
- 数据库里已有的设备(含历史播种的、用户自建的)在未启动会话时**界面上不可见**,
  无法"点击启动"。

## 决策

1. **移除 `--demo-session`**:参数、Bootstrap.startDemoSession、演示设备播种
   (seedDefaultDevices)全部删除;`--config` 保留为显式的"导入并启动"动作。
   demo-etch/demo-cvd JSON 降级为**测试与实机资产**(host-e2e、NativeRuntimeIT 用
   `--config <文件>` 显式启动),不再进入任何启动路径。
2. **设备目录以数据库为准**:工作台「设备与会话」表数据源扩为
   **活动会话 ∪ 数据库设备**——未启动的设备显示为「停止」状态行,行内唯一动作是
   「启动」(按配置 `POST /api/v1/sessions` 创建会话);不参与批量勾选,设备名不可点。
3. **启动语义不变**:停止/断开仍是"断链不删实体",重启进程后**不会**自动恢复任何会话
   (该语义 3.0 起就成立,本次只是移除了唯一的例外)。

## 后果

- 进程起来即是纯 API/界面形态(sessions=0),首次启动列表为空,「新建设备」创建设备;
- 壳/安装包打开后不再自动有演示设备,列表展示数据库内容(停止态);
- host-e2e、NativeRuntimeIT 改用 `--config` 显式启动演示设备;
- 会话仍不写回"应自动恢复"标记——重启后一切从停止态开始,由人拉起。

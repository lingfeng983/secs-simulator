## P1 — 严重（必现，功能不可用）

### 问题 1：访问不存在的设备时整页白屏（React #300），空态永不显示

- **现象**：浏览器打开 `#/device/ghost/runtime/plans`（或任意不存在的设备 id），
  主内容区完全空白，控制台报 `Minified React error #300`（渲染的 hooks 数量前后不一致），
  代码里写好的「设备 ghost 不存在」空态提示根本不会出现。
- **复现**：稳定复现，连续 3 次测试 3/3 白屏，pageerror 均为 1。
  - E2E 对应用例：`scripts/e2e/app.spec.ts:183`「设备不存在时给出空态并可回设备清单」——实测失败。
- **根因**：`src/features/pages/DevicePage.tsx` 第 133–148 行的 `if (!sessionKnown) return <空态/>`
  这个 early return 位于第 151 行 `useDirtyPages(...)` **等 hooks 之前**。
  首屏数据未加载时 `sessionKnown=false` 走 early return（少渲染几个 hooks），
  数据加载后变 true 就会执行到后面的 hooks，hooks 数量突变 → React 抛 #300 并卸载整棵树。
- **影响**：用户手输/收藏了旧设备地址、或设备被删除后再次访问深链，看到的是白屏而非可操作的空态，
  无法识别发生了什么，也无法"回设备清单"。
- **修复建议**：把空态的 early return 移到 `DevicePage` 内**所有 hooks 调用之后**
  （即第 151 行 `useDirtyPages` 及之后的所有 hook 都执行完再判断 `sessionKnown`）；
  或改为 `return <DevicePageEmpty .../>` 由父组件在无 session 时不挂载本组件。
- **截图**：`screenshots/verify-ghost-device.png`、`screenshots/verify-ghost-config.png`

## P2 — 中等（功能异常，有明确正确行为被破坏）

### 问题 2：「事件执行」页的单步试跑对配置内计划必然失败（前后端计划数据源不一致）

- **现象**：设备·运行区「事件执行」页，对列表里的计划（如 `StartPlan` / `EndPlan`）
  点「单步试跑」，后端返回 **HTTP 500 `{"ok":false,"error":"plan-step-failed"}`**，
  日志报 `单步试跑计划失败: StartPlan: java.io.IOException: plan not found: StartPlan`。
- **复现**：
  ```
  curl -X POST http://127.0.0.1:5000/api/v2/devices/ETCH01/runtime/plans/StartPlan/step
  # -> HTTP 500  plan-step-failed
  ```
  而 `GET /api/v1/sessions/ETCH01/events` 明明返回了 id 为 `StartPlan` 的计划。
- **根因**：`EventReporter.step()`（`secs-runtime/.../session/EventReporter.java:247-255`）
  查的是 `EventScheduler.schedule.plans()`（配置 v1 编排计划集），
  而前端「事件执行」页展示的是 v2 运行时计划（`plansV2Json` / `runtime_plan_override`），
  两者是**不同的计划集合**：界面上看到的计划 id 在 step 的执行器里根本不存在。
- **影响**：单步试跑这个调试能力对界面上可见的计划完全不可用，用户无法手动验证一条计划会发生什么。
- **修复建议**：让 step 端点的计划查找与 `plansV2Json` 使用同一份数据源
  （v2 运行时计划覆盖表 + 配置计划合并后的集合），或在 UI 上明确区分"可试跑"的计划来源。
- **截图**：`screenshots/buttons/13-device-runtime-plans_b*.png`

### 问题 3：报警风暴在设备已在线/有活动报警时返回 409

- **现象**：设备·运行区「手动与压测」页点「报警风暴」，控制台出现
  `Failed to load resource: 409 (Conflict)`。
- **复现**：`button-test-report.json` 中 `15-device-runtime-manual` 的「报警风暴」按钮触发 409。
- **分析**：后端对并发压测/报警风暴有互斥保护（同一设备同时只允许一个风暴任务），
  连续触发或前一次未结束时再次触发会返回 409。
- **影响**：属**预期内的并发保护**，但前端当前未把 409 翻译成友好提示
  （用户只看到一条资源加载失败，不知道是"上一次还没跑完"）。
- **修复建议**：前端捕获 409 并提示"已有压测正在进行，请等待结束"；
  测试脚本层面属于连续快速点击的副作用，非阻断性缺陷。
- **截图**：`screenshots/15-device-runtime-manual.png`

### 问题 4：用户手册（user-guide.md）与 3.2 实际界面明显不一致

- **现象**：`docs/guides/user-guide.md` 描述的是旧版信息架构，与当前界面不符：
  - 手册写"左侧导航分三组：**总览 → 设备 → 主机**"，实际是"设备 / 主机清单 / 独立工具"
    （见 `src/app/layout/navigation.ts`）；
  - 手册写"设备组支持**按名称/模板筛选，并可切换平铺/按模板分组**"，
    而 3.2 的 E2E 明确断言这些能力"全部下线"；
  - 手册写"主机模拟分**五个子页**"，实际主机详情是配置区 4 页 + 运行区 3 页；
  - 手册列的设备子页（"事件与报告/状态变量/手动操作"在运行区）与当前两区划分有出入。
- **影响**：新用户照手册操作会找不到菜单项（筛选、分组切换、总览组），产生困惑。
- **修复建议**：按 3.2 的 `navigation.ts` / `router.ts` 重新校对手册第 2、3 节。

## P3 — 轻微（可用性/体验）

### 问题 5：审计日志被周期性查询刷屏

- **现象**：`#/system/audit` 页出现大量重复的 `plan-executions / limit=100` 记录，
  约每 10 秒一条，把真正有意义的运维操作（建设备、连接、上下线）淹没。
- **截图**：`screenshots/27-audit.png`（可见连续多条相同记录）。
- **分析**：前端对执行台账的定时轮询被后端记成了审计事件。
  审计应只记"人的操作"，不应记"读查询/自动轮询"。
- **修复建议**：审计记录排除 GUI 自动轮询的只读请求，或前端轮询走不带审计标记的只读端点。
